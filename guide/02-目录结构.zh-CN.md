# 02 · 目录结构
**[English](02-目录结构.md)** · 简体中文

> 这一章回答：**东西该放在哪。**
> 依据同样来自三处：GitHub 的位置规则、agent 工具加载指令文件的方式、以及真实仓库的实际布局（下面的实测）。
> 全章用通用术语指代各类工具机制；通用术语与具体文件名的对照见 [机制对照表](../spec/mechanism-map.md)（附录，非规范）。

---

## 0. 一条总原则

**根目录是"入口区"，不是"仓库"。**

根目录的职责是让陌生人在 30 秒内找到入口；一切"细节"都该下沉到子目录。
判断标准很简单：**根目录里每个文件，都能用一句话说出"谁会在什么情况下点开它"吗？** 说不出来的，就是错位了。

---

## 1. 先看实测

同一批仓库（见 [01 章](01-该有什么文档.zh-CN.md) 的样本），目录形态如下：

| 仓库 | 文档目录 | `.github/` 内容（摘要） | 根目录文件数 |
|---|---|---|---|
| cli/cli | `docs/` | CONTRIBUTING、SECURITY、CODE-OF-CONDUCT、ACCESSIBILITY、CODEOWNERS、ISSUE_TEMPLATE、PULL_REQUEST_TEMPLATE、**agents/**、**skills/**、workflows、actions、dependabot、mcp.json | 少（多为入口 + 构建文件） |
| microsoft/vscode | —（文档在 wiki/站点） | CODEOWNERS、pull_request_template、ISSUE_TEMPLATE、**平台级指令文件**、**agents/**、**skills/**、**instructions/**、**hooks/**、rulesets、learnings、commands | 多（构建/配置为主） |
| vercel/next.js | `docs/` | **AGENTS.md**、CODEOWNERS、ISSUE_TEMPLATE、DISCUSSION_TEMPLATE、workflows | 多 |
| modelcontextprotocol/servers | `docs/` | ISSUE_TEMPLATE、pull_request_template、workflows | 少 |
| sindresorhus/got | `documentation/` | ISSUE_TEMPLATE、PULL_REQUEST_TEMPLATE、security.md、workflows | 少 |
| python/cpython | `Doc/` | ISSUE_TEMPLATE、workflows、CODEOWNERS | 多 |

读出来的四件事（各仓库 `.github/` 里实测到的原始文件名见[证据 §3](../docs/evidence/2026-11-17-repo-sampling.md)）：

1. **`.github/` 是 100% 存在的**（10/10），而且已经在承担"平台文件 + agent 指令"两个职责。
2. **文档目录名不统一**：`docs/`、`Doc/`、`documentation/` 都是真实存在的。**新建时统一用 `docs/`，存量的不要为了改名去重构。**
3. **根目录文件数差异巨大**：`got` 只有几个，`vscode` 有几十个——根目录的密度取决于构建方式（有没有 monorepo 工具、有没有大量配置），**不是"越干净越好"**。
4. **agent 相关的东西有两种放法**：`cli/cli` 和 `vscode` 放 `.github/agents`、`.github/skills`；只服务单一工具的那套放它自己的资产目录。

## 2. 根目录：三色清单

### 必须有（入口类）

| 文件 | 为什么必须在根 |
|---|---|
| `README.md` | GitHub 按 `.github/` > 根 > `docs/` 取第一个；根是默认位置 |
| `LICENSE` | 协议必须一眼可见 |
| `.gitignore` | 工具默认读根 |
| `AGENTS.md` | agent 默认读根；放别处读不到 |

### 可以有（平台要求或工程必需）

`.github/`、`CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md`、`CODE_OF_CONDUCT.md`、
`package.json` / `pyproject.toml` / `go.mod`、`Makefile`、`.editorconfig`、`.gitattributes`、工具专属指令文件、`.mcp.json`

### 不要放

| 不该在根目录 | 应该去哪 |
|---|---|
| 架构文档、教程、长指南 | `docs/`（根只留链接） |
| 会议记录、临时笔记 | `docs/notes/` 或干脆别提交 |
| 生成物、构建缓存、日志 | `.gitignore` 掉 |
| 十来个脚本 | `scripts/`（并在 README 里写明用途） |
| 各环境的配置副本 | `configs/`，或用环境变量 |
| 一个目录只装一个文件 | 合并或下沉 |

## 3. `.github/`：平台文件与"跨工具 agent 文件"

`.github/` 是 GitHub 唯一认的位置集合，实测里它同时装两类东西：

**① 平台文件（GitHub 只认这里）**

```
.github/
├── CODEOWNERS                    # 也可以放根或 docs/
├── CONTRIBUTING.md               # 人读的贡献指南（根/.github/docs 均可）
├── SECURITY.md                   # 私密上报入口
├── ISSUE_TEMPLATE/{bug.yml,feature.yml,config.yml}
├── PULL_REQUEST_TEMPLATE.md
├── dependabot.yml
└── workflows/*.yml               # Actions 只认这个路径
```

**② 跨工具的 agent 文件（可选，但已是头部仓库的做法）**

`cli/cli` 与 `microsoft/vscode` 的实际布局：

```
.github/
├── agents/            # agent 角色/工作流定义（cli/cli: code-review、dependabot-triager…）
├── skills/            # 可复用流程
├── instructions/      # 分主题的指令片段（vscode）
├── hooks/             # 工具钩子（vscode）
├── <平台级指令文件>    # 代码托管平台为 agent 留的指令位（vscode）
└── AGENTS.md          # next.js 把 AGENTS.md 也放了一份在这里
```

> **判断规则**：这份内容**只服务一个工具** → 那个工具自己的资产目录；**多个工具都要用** → `.github/`。

## 4. `docs/`：分层，不要摊平

### 推荐骨架

```
docs/
├── index.md            # 地图：按下面五类给入口
├── getting-started/    # 教程：从零到跑起来
├── guides/             # 任务导向：怎么做某件事
├── reference/          # 查阅型：API、配置项、错误码
├── architecture/       # 现状说明：模块、数据流
├── adr/                # 决策记录：为什么不是另一种
└── operations/         # 运维：部署、回滚、on-call
```

### 三条写法

- **`index.md` 是地图，不是散文。** 读者到这里是为了"点进去"，不是"读一段话"。
- **一个文件一个主题，文件名即主题。** `docs/adr/0007-cursor-pagination.md` 比 `docs/design2-final.md` 有用一个数量级。
- **长内容不进 README。** README 只回答"要不要用、怎么跑起来"，其余下沉。

### 命名不要较真

`Doc/`（cpython）、`documentation/`（got）都是真实存在的。**新建用 `docs/`，存量不必改名**——
改名会让所有外部链接失效，收益远小于成本。

## 5. agent 相关：工具专属资产目录还是 `.github/`

同一个概念，两处路径。对照表（每一行对应的具体文件名见[机制对照表](../spec/mechanism-map.md)）：

| 概念 | 单一工具把它放在哪 | 跨工具/GitHub 生态常见路径 | 建议 |
|---|---|---|---|
| 项目指令 | `AGENTS.md`（根/子目录）、工具专属指令文件 | `AGENTS.md`、平台级指令文件 | **`AGENTS.md` 放根**，需要时在平台级文件里只放指针 |
| 权限与 hooks | 共享工具配置文件（权限与 hook 声明） | `.github/hooks/`（vscode 的做法） | 只服务单一工具 → 该工具的资产目录 |
| 分主题规则 | 该工具的分层机制（带路径作用域的规则文件） | `.github/instructions/*`（vscode） | 只服务单一工具 → 该工具的资产目录 |
| 可复用流程 | 工具资产目录里的 skill 文件 | `.github/skills/`（cli/cli、vscode） | 多工具用 → `.github/skills/` |
| 子代理 | 工具资产目录里的子代理定义 | `.github/agents/`（cli/cli、vscode） | 同上 |
| 单文件命令 | 工具资产目录里的单文件命令定义 | `.github/commands/`（vscode） | 同上 |
| MCP 服务 | `.mcp.json`（项目根） | `.github/mcp.json`（cli/cli） | 团队共享就进版本库 |

记这一条就够：**只服务单一工具的放那个工具自己的资产目录，任何别的工具也可能用的放 `.github/`。**
不要两边各写一份——那就是双事实源。

## 6. 大仓与 monorepo：分两种模式

### 官方做法：按目录分层加载

若你的工具自带分层机制，官方给大仓的做法是（具体文件名与配置键见[机制对照表](../spec/mechanism-map.md)）：

- **在根放共享约定，在每个包/子系统下再放一份**（`packages/api/<指令文件>`、`packages/web/<指令文件>`）；
- 根文件在启动时加载，**子目录文件只在你读到那里时才加载**；
- 不想要的包可以用该工具的"指令文件排除项"排除；
- 也可以改用该工具的分层机制（带路径作用域的规则）代替一堆子目录文件；
- 每个目录可以有**自己的 skills**。

### 实测的两种极端

| 模式 | 代表 | 特征 | 适合 |
|---|---|---|---|
| **路由型** | `microsoft/vscode`：根 `AGENTS.md` 只有 **8 行**（271 字节），指向平台级指令文件 | 根文件只做索引，细则在别处 | 大仓、多团队、细则已经分文件维护 |
| **指针+边界型** | `python/cpython`：根 `AGENTS.md` **约 1KB**，指到外部 AI 政策 + 5 条原则 + "不要用 AI 自动开 issue" + 去重命令 | 根文件只放"必须立刻知道"的 | 有外部治理政策的项目 |
| **大全型** | `vercel/next.js` 33 KB、`modelcontextprotocol/servers` 51 KB；`cli/cli` 5.8 KB | 根文件承载全部约定 | 单团队、约定集中、能保证不腐烂 |

### 看一个真实的路由型（`microsoft/vscode`，全文 8 行）

```markdown
# VS Code Agents Instructions

This file provides instructions for AI coding agents working with the VS Code codebase.

For detailed project overview, architecture, coding guidelines, and validation steps, see the
platform-level instruction file.

Prefer `CancellationToken`/`CancellationTokenSource` internally and adapt `AbortSignal` only at native or
third-party API boundaries; see the cancellation guidance.
```

（引文里点到某家文件名的那一句做了中性化转述；8 行原文与原始文件名见
[2026-11-18 采样](../docs/evidence/2026-11-18-agent-docs-sampling.md)。）

它只做两件事：**指向真正的细则**，以及**把最容易做错的那一条写在门口**。
（"内部用 `CancellationToken`，只在边界上转 `AbortSignal`"——这一条 agent 猜不出来，但每次都会踩。）

把这种形态抄成一整份可读文件：[examples/small-repo/AGENTS.md](../examples/small-repo/AGENTS.md)。

**怎么选**：先写"大全型"的**最小版本**（命令 + 禁区 + 坑），超过 200 行就拆成"路由型"——
把细则移进该工具的分层机制或子目录 `AGENTS.md`，根文件只留指针与边界。

## 7. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 根目录堆 30 个文件 | 新人找不到入口；agent 也读不完 | 下沉到 `docs/`、`scripts/`、`configs/` |
| agent 指令写进 README | 工具读不到，人看着是噪音 | 拆出 `AGENTS.md` |
| 文档全塞根目录 | 根目录变成第二份 docs | 只留入口，其余进 `docs/` |
| `docs/` 里放构建产物 | 仓库膨胀、diff 噪音 | `.gitignore` |
| 工具专属资产目录与 `.github/` 各存一份 agent 规则 | 双事实源，随机生效 | 按"谁用"选一处，另一处只放指针 |
| 子目录 `AGENTS.md` 互相矛盾 | agent 加载后行为漂移 | 子文件只写"这一目录的差异"，不重复根约定 |
| 为了统一命名把 `Doc/` 改成 `docs/` | 外部链接全断 | 新建用 `docs/`，存量不动 |
| 把个人覆盖文件当配置模板提交 | 泄露本机路径 | 只提交共享工具配置文件 |
