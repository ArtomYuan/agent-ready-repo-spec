# 01 · What documents a repository should have

**English** · [简体中文](01-该有什么文档.zh-CN.md)

> This chapter answers one question: **which documents should a GitHub repository have?**
> The basis is not my preference but three things: **GitHub's own recognition rules**, **how agent tools load
> instruction files**, and **the actual layout of ten real repositories** (table below).
> Generic terms for tool mechanisms are used throughout; their mapping to concrete file names lives in the
> [mechanism map](../spec/mechanism-map.md) (appendix, non-normative).

Four things to read out of it:

1. **README + LICENSE + `.github/` are 10/10.**
2. **CONTRIBUTING / SECURITY / CoC are often not at the root** — they live under `.github/`. Only 6/10 keep a root CONTRIBUTING.
3. **`AGENTS.md` is already common** (6 of the 10 top repositories sampled); **the tool-specific instruction file is the exception** (1/10 — and that one is the tool vendor's own repo). The sample is non-random and skews to large open-source repos: it shows *that* the practice exists, not that most repositories do it.
4. **The docs directory name is not standardised**: `docs/`, `Doc/`, `documentation/` all exist — so any rule that
   demands the name `docs` will misfire on real repositories.

## 1. Three tiers

Documents are not "the more the more professional". Split them by **who needs them** — the cost of missing each tier
is completely different.

### Tier 1 — the platform needs it (missing = directly less usable)

| File | How GitHub recognises it | If missing |
|---|---|---|
| `README.md` | takes the **first** of `.github/` > root > `docs/` | the repo homepage is blank; nobody can judge "should I use this" |
| `LICENSE` | root; `LICENSE.md` / `COPYING` also recognised | defaults to "all rights reserved"; others cannot legally use it |
| `.github/CONTRIBUTING.md` | root / `.github/` / `docs/`; **file name is case-insensitive**; `.rst` also recognised | no "read this before contributing" prompt when opening an issue/PR |
| `.github/SECURITY.md` | same three locations | no private disclosure route; vulnerabilities land in public issues |
| `.github/ISSUE_TEMPLATE/*.yml` | **only** `.github/ISSUE_TEMPLATE/` | no template chooser; the community profile doesn't tick |
| `.github/PULL_REQUEST_TEMPLATE.md` | `.github/` or root (either case) | PR description quality depends on goodwill |
| `.github/CODEOWNERS` | `.github/` / root / `docs/` | review relies on @-mentioning people; things get missed |

Two boundaries people trip over:

- **GitHub recognises files at fixed locations, not "directories".** A `contributing/` directory alone does not count —
  there must be an entry file pointing at it (`github/docs` does exactly this: `.github/CONTRIBUTING.md` points at the
  long-form `contributing/` directory).
- **Organisation-wide defaults are configured once**: put `CONTRIBUTING` / `SECURITY` / `CODE_OF_CONDUCT` /
  `ISSUE_TEMPLATE` into a **public repository named `.github`**; it applies to the whole org, and a repo-local file of
  the same name overrides it.

### Tier 2 — collaboration needs it (missing = collaboration distorts)

| File | Responsibility | When you can skip it |
|---|---|---|
| `CHANGELOG.md` | records "user-visible behaviour changes"; the basis for upgrading | never releases, or a purely internal experiment |
| `CONTRIBUTING.md` | branching model, commit format, PR flow, review SLA | private repo with no external PRs |
| `CODE_OF_CONDUCT.md` | community standards and a reporting path | internal repo, or all contributors are in one team |
| `SUPPORT.md` | routes "how do I use this / where do I ask" away from issues | usually unnecessary once Discussions or a forum exists |
| `ACCESSIBILITY.md` | accessibility goals, known barriers, reporting path (`cli/cli` has one) | libraries with no UI |
| `GOVERNANCE.md` / `MAINTAINERS.md` | who may merge, how to become a maintainer | solo project |
| `CITATION.cff` | canonical citation when the work is referenced | non-academic projects |

### Tier 3 — the agent needs it (missing = the agent guesses)

| File | Who reads it | If missing |
|---|---|---|
| **`AGENTS.md` (root)** | agent tools that follow the open convention, **loaded in full every session** | the agent doesn't know the commands, the layout, or the forbidden areas — it guesses from the code |
| `AGENTS.md` (subdirectories) | same, loaded when work enters that directory | the root file is forced to become an encyclopaedia |
| Tool-specific instruction file | when your tool reads its own file besides `AGENTS.md` | you lose a thin layer; not essential |
| Shared tool configuration file | if your tool reads a committed permission/hook declaration | no shared permission baseline; every machine gates differently |
| Skill files under the tool-specific asset directory | loaded when a task matches | multi-step procedures get crammed into AGENTS.md and eat the budget |
| Subagent definitions under the tool-specific asset directory | when a subagent is dispatched | no context isolation |
| Platform-level instruction file | if your agent reads the hosting platform's instruction slot | only needed if that slot exists in your setup |

**Why `AGENTS.md` comes first**: 6/10 of the surveyed top repositories already have it; agent tools **read it by
default** when there is no tool-specific instruction file; and the tool-specific instruction file appears in one
vendor's own repository alone.
**The cross-tool common denominator is `AGENTS.md`, not a tool-specific instruction file.**

## 2. Deciding whether to write each file

Three questions, in order — faster than memorising the lists:

```
1. Will anyone use this repository from the outside?
   ├─ yes → README + LICENSE + .github/SECURITY.md + .github/CONTRIBUTING.md
   └─ no  → README + LICENSE (recommended even internally) + AGENTS.md

2. Will anyone submit PRs?
   ├─ yes → + CODEOWNERS + PR template + CHANGELOG + code of conduct
   └─ no  → skip these (the PR template is still useful: it constrains your own PR descriptions)

3. Will an agent work on this?
   └─ yes → + AGENTS.md (essential) + the shared tool configuration file (if you want gates) + skills (for procedures with side effects)
```

## 3. The minimum for day one

Not "six files at once", but **add in order, each one with a clear payoff**:

| When | Add | Why |
|---|---|---|
| Day 1 | `README.md`, `LICENSE`, `.gitignore`, `AGENTS.md` | without these four, nobody — human or otherwise — can take over |
| Week 1 | `.github/workflows/ci.yml`, PR template | without CI there is nowhere to hang any later gate |
| Month 1 | `CHANGELOG.md`, `CODEOWNERS`, `.github/SECURITY.md` | versions, review, and an external surface start to exist |
| Later | `docs/` + ADRs, `CONTRIBUTING.md`, skills | decisions start accumulating and procedures start repeating |

## 4. Three boundaries that are easy to get wrong

**① CONTRIBUTING is written for humans, not for the agent.**
It is not in the loading chain of agent tools (zero mentions in the memory documentation quoted in
[evidence excerpt §2](../docs/evidence/2026-11-17-claude-code-docs.md)). To make an agent follow contribution rules,
put a pointer in `AGENTS.md` — `cli/cli` writes: `Read CONTRIBUTING, the canonical contribution policy.`

**② SECURITY / CoC are only required when there is an external surface.**
Measured: `microsoft/vscode`, `anthropics/claude-code`, `modelcontextprotocol/servers` keep `SECURITY.md`;
`cli/cli`, `next.js`, `rust` do not have one at the root, but they do under `.github/` (`cli/cli` also has
`VULNERABILITY_REPORT.yml`). What matters is **"is there a private reporting route"**, not "is there a file at the root".

**③ A CHANGELOG is not a git log.**
Only 3/10 have `CHANGELOG.md` at the root — not because it is unimportant, but because many use release notes instead.
The criterion is not "does the file exist" but **"can a user find out what changed in a given version"**.
