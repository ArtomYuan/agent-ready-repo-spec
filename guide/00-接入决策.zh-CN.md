# 00 · 接入决策：一次选好，落在被管理的库里

**[English](00-接入决策.md)** · 简体中文

> 这套规范是**指导性**的：用不用、用多少，由采用它的仓库决定。
> 但"决定"必须是**显式的一次性动作**，并且**留在被管理的那个仓库里**——
> 否则半年后没人知道当初选了哪一档、哪些是故意没做。
>
> 全章用通用术语指代各类工具机制；通用术语与具体文件名的对照见
> [机制对照表](../spec/mechanism-map.md)（附录，非规范）。

---

## 0. 三条规矩

1. **一次选好**：接入时做一次决策，之后按需修订，不要每次体检重新讨论。
2. **决定要落地**：每个"采用"必须有一个**执行点**——门禁、共享工具配置文件里的一条声明、CI job、或 `AGENTS.md` 里的一节。
   **没有落点的"采用"等于没采用。**
3. **记录留在被管理的库**：决定写在使用者的仓库里（ADR、`AGENTS.md`、或独立的采用记录），
   不写在规范库里。规范库只提供选项与判据。

三条合起来的意思是：**这个库不替你做决定，但要求你的决定是可查的。**

---

## 1. 可选项一览

按"决定域"分七组。左列是决定，右列是**它必须落在哪里**才算数。

| # | 决定 | 取值 | 落点（缺了就不算采用） |
|---|---|---|---|
| 1 | **目标等级** | L1 / L2 / L3 | 写进采用记录；CI 里的 `-Level` 参数 |
| 2 | **PR 门禁** | 关闭 / 必须 PR / 必须 PR + 审批 | 分支保护：`Require a pull request`、`Required approvals` |
| 3 | **管理员是否可绕过** | 可绕过 / 不可绕过 | 分支保护：`Do not allow bypassing` |
| 4 | **必需检查** | 无 / 指定 job 名 | 分支保护：`Required status checks` + CI 里真实存在的 job |
| 5 | **提交规范** | 仅文档约定 / commitlint | `commitlint` 配置 + CI 里的 job；仅约定则落 `AGENTS.md` |
| 6 | **agent 归属** | 保留默认 trailer / 自定义 / 关闭 | 共享工具配置文件里的 `attribution` |
| 7 | **agent 指令形态** | 单根文件 / 根 + 子目录分层 / 路由型 | `AGENTS.md`（+ 子目录文件） |
| 8 | **权限基线** | 无 / 权限声明（deny 清单） | 共享工具配置文件 |
| 9 | **硬约束形态** | 只写文档 / 上门禁 hook / 上 CI | 共享工具配置文件里的 hook 声明、或 CI workflow |
| 10 | **文档集** | 取哪些（CONTRIBUTING / SECURITY / CoC / CHANGELOG / ADR…） | 对应文件本身 |
| 11 | **记录与复审** | ADR 触发条件、复审周期 | `docs/adr/`、采用记录 |

> 说明：第 2–4 项属于**平台设置**，任何检查器都读不到，只能靠"记录 + 人工核对"；
> 第 5–9 项属于**仓库内文件**，可以被工具验证；第 10–11 项是内容，靠评审。

## 2. 决策怎么记录

三种载体，任选其一（建议 1 或 2）：

| 载体 | 适合 | 特点 |
|---|---|---|
| **独立采用记录** `docs/adoption.md` | 想把"用了哪些、没用什么、为什么"一页看完 | 最容易复查；不挤占 ADR 编号 |
| **ADR**（`docs/adr/000N-adopt-...md`） | 已经有 ADR 习惯、且这次接入本身就是一个"架构级决定" | 复用现有流程；但一个 ADR 只该记一个决定，接入往往包含多条 |
| **`AGENTS.md` 里一节** | 小仓库、决策很少 | 人看不到；但 agent 每次都会读到——**这一点很关键** |

无论用哪种，内容都要包含四样：**采用日期 / specVersion、目标等级、每项决定与落点、未采用项及理由**。

模板见 `templates/adoption.md.tmpl`。

### 为什么"未采用"也要写

- 不写，下一个人（或下一个 agent）会把它当成"漏了"，然后"顺手补上"——很可能补错；
- 写了，它就是一个**可被质疑的决定**：理由站不住脚时，别人可以推翻它，而不是猜你的意图。

## 3. 一个最小示例

```markdown
# 采用记录：agent-ready-repo-spec

- specVersion：1.4.0
- 采用日期：2026-11-17　决策人：@alice
- 目标等级：**L2**

| 决定 | 选择 | 落点 |
|---|---|---|
| PR 门禁 | 必须 PR + 检查 | 分支保护 `Require a pull request` + 4 个 required checks |
| 管理员绕过 | **不允许** | 分支保护 `Do not allow bypassing` |
| 提交规范 | commitlint | `.commitlintrc.json` + CI job `commits` |
| agent 归属 | 保留默认 `Co-Authored-By` | 不设置 `attribution`（即默认） |
| agent 指令 | 根 `AGENTS.md` + 两个子目录 | `AGENTS.md`、`packages/api/AGENTS.md` |
| 文档集 | README / LICENSE / SECURITY / CHANGELOG / ADR | 对应文件 |

**未采用**

- `CONTRIBUTING.md`：私有库、不收外部 PR。**若将来接受外部贡献，先补它。**
- `CODE_OF_CONDUCT.md`：同上。

**复审**：2027-01-31，或开始接受外部贡献时。
```

## 4. 接入时怎么走（五步）

1. **对着 [清单](../spec/rules/README.md) 过一遍**：得到现状（这是事实，不是评分）。本库不提供检查器，只能人工或由 agent 逐条比对。
2. **定目标等级**：L1 够用就别硬上 L3——等级越高，需要维护的东西越多。
3. **逐项做决定**：从上表挑出与你相关的项，写下"采用 / 不采用 + 理由 + 落点"。
4. **把落点做出来**：门禁去平台开、共享工具配置文件去写、CI job 去加。**这一步不做，前面全是文档。**
5. **记下来**：写采用记录或 ADR，并写上复审时间。

之后每次体检，只对照**你自己定的目标等级**看清单，不要拿别人的档位要求自己。

## 5. 三个常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| "既然规范里有，就都做了" | 维护成本失控，最后没人守 | 按目标等级与团队规模做减法 |
| "先写在文档里，门禁以后再说" | 半年后还是没门禁，但大家都以为有 | 没有落点就标为"未采用" |
| "照抄别人的采用记录" | 组织信息（谁审批、SLA 几天）不同 | 抄结构，不抄结论 |

## 6. 这个库自己怎么做的

本仓库就是这套规矩的第一个使用者：

- 采用记录 = [ADR-0004](../docs/adr/0004-all-changes-via-pr.md)（门禁与 PR 流程）+ [ADR-0003](../docs/adr/0003-why-this-repo-delays-admin-enforcement.md)（已被取代的旧决定，保留作历史）；
- 落点 = main 的 ruleset（必须 PR + 必需检查 + 一条人工批准）+ 本文件的清单对照；
- **未采用项**：对 `rules/README.md` 的机器校验、agent 权限基线（共享工具配置文件）——本库只保留文档自身的一致性检查（链接检查 / 双语配对），见 [ADR-0009](../docs/adr/0009-spec-only-no-tooling.md)。
- **CODEOWNERS 目前只是索引**：ruleset 没开 `Require review from Code Owners`，它不会自动指派评审——要开的话见 [guide/07](07-该开哪些设置.zh-CN.md) §2。
- **已采用但暂时无用**：`CODE_OF_CONDUCT.md`（有外部贡献者时才真正有意义，先放着）。

按第 0 节第 2 条自检：**我们每个"采用"都有落点**——这条可以拿去核对任何一个声称"接入了这套规范"的仓库。
