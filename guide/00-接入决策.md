# 00 · Adoption decisions: decide once, record it in the adopting repository

**English** · [简体中文](00-接入决策.zh-CN.md)

> This spec is **guidance**: whether — and how much — to use it is up to the repository adopting it.
> But the decision must be an **explicit, one-time act**, and it must **live inside the adopting repository** —
> otherwise, six months later, nobody knows which tier you picked and which gaps were deliberate.

---

## 0. Three rules

1. **Decide once.** Make the decision when you adopt; revise it when needed. Don't re-litigate it at every audit.
2. **Every decision needs an enforcement point** — a gate, a `settings.json` entry, a CI job, or a section in `AGENTS.md`.
   **An "adopted" option with no enforcement point is not adopted.**
3. **Keep the record in the adopting repository** — in an ADR, in `AGENTS.md`, or in a standalone adoption record.
   This repository only supplies options and criteria.

Together: **this library does not decide for you, but it requires your decision to be inspectable.**

---

## 1. The options

Seven decision areas. The left column is the decision; the right column is **where it has to land** to count.

| # | Decision | Values | Enforcement point (missing = not adopted) |
|---|---|---|---|
| 1 | **Target level** | L1 / L2 / L3 | the adoption record; the `-Level` argument in your CI |
| 2 | **Pull-request gate** | off / PR required / PR + approvals | branch protection: `Require a pull request`, `Required approvals` |
| 3 | **Can admins bypass?** | yes / no | branch protection: `Do not allow bypassing` |
| 4 | **Required checks** | none / named jobs | branch protection: `Required status checks` + jobs that actually exist in CI |
| 5 | **Commit convention** | documented only / commitlint | `commitlint` config + a CI job; if documented only, a section in `AGENTS.md` |
| 6 | **Agent attribution** | default trailer / custom / off | `attribution` in `.claude/settings.json` |
| 7 | **Shape of the agent instructions** | single root file / root + per-directory / router | `AGENTS.md` (+ per-directory files) |
| 8 | **Permission baseline** | none / a `permissions.deny` list | `.claude/settings.json` |
| 9 | **Hard constraints** | docs only / hook / CI | `hooks` in `.claude/settings.json`, or a workflow |
| 10 | **Document set** | which ones (CONTRIBUTING / SECURITY / CoC / CHANGELOG / ADR …) | the files themselves |
| 11 | **Record and review** | ADR trigger conditions, review cadence | `docs/adr/`, the adoption record |

> Note: items 2–4 are **platform settings** — no checker can read them, so they rely on "record + human check".
> Items 5–9 are **files inside the repo** and can be verified by tooling. Items 10–11 are content; they rely on review.

## 2. How to record the decision

Pick one of three carriers (1 or 2 recommended):

| Carrier | Good for | Notes |
|---|---|---|
| **A standalone adoption record** `docs/adoption.md` | seeing "what we use, what we don't, and why" on one page | easiest to review; doesn't consume ADR numbers |
| **An ADR** (`docs/adr/000N-adopt-...md`) | teams that already use ADRs, and where adoption itself is an architectural decision | reuses the existing process; but one ADR should hold one decision, and adoption usually contains several |
| **A section in `AGENTS.md`** | small repositories with few decisions | humans won't see it; but the agent reads it every session — **which matters a lot** |

Whichever you choose, it must contain four things: **adoption date / specVersion, target level, each decision with its
enforcement point, and the options you did NOT adopt with reasons.**

Template: `templates/adoption.md.tmpl`.

### Why record what you did *not* adopt

- If you don't, the next person (or the next agent) reads it as an oversight and "helpfully" fills it in — often wrongly;
- If you do, it becomes a **decision that can be challenged**: a weak rationale can be argued against, instead of guessed at.

## 3. A minimal example

```markdown
# Adoption record: agent-ready-repo-spec

- specVersion: 1.3.0
- Adopted: 2026-11-17   Decision owner: @alice
- Target level: **L2**

| Decision | Choice | Enforcement point |
|---|---|---|
| PR gate | PR required + checks | branch protection `Require a pull request` + 4 required checks |
| Admin bypass | **not allowed** | branch protection `Do not allow bypassing` |
| Commit convention | commitlint | `.commitlintrc.json` + CI job `commits` |
| Agent attribution | keep default `Co-Authored-By` | leave `attribution` unset (i.e. default) |
| Agent instructions | root `AGENTS.md` + two subdirectories | `AGENTS.md`, `packages/api/AGENTS.md` |
| Document set | README / LICENSE / SECURITY / CHANGELOG / ADR | the files themselves |

**Not adopted**

- `CONTRIBUTING.md`: private repo, no external PRs. **If that changes, add it first.**
- `CODE_OF_CONDUCT.md`: same reason.

**Review**: 2027-01-31, or when external contributions start.
```

---

## 4. How to adopt (five steps)

1. **Run the self-check once**: `spec-check.ps1 -Target .` — that gives you the current state (facts, not a grade).
2. **Pick a target level**: if L1 is enough, don't force L3 — every level up costs maintenance.
3. **Decide item by item**: from the table above, write "adopt / don't adopt + reason + enforcement point".
4. **Build the enforcement points**: turn the gates on, write `settings.json`, add CI jobs.
   **Without this step, everything above is just prose.**
5. **Record it**: write the adoption record or ADR, including the review date.

From then on, audit yourself against **the target level you chose** — don't measure yourself against someone else's tier.

---

## 5. Three common mistakes

| Mistake | What goes wrong | Do instead |
|---|---|---|
| "The spec has it, so we do all of it" | maintenance cost explodes; nobody keeps it up | subtract, based on target level and team size |
| "Write it in the docs now, wire the gates later" | a year later there are still no gates, but everyone assumes there are | if there's no enforcement point, mark it "not adopted" |
| "Copy someone else's adoption record" | organisation-specific facts (approvers, SLAs) differ | copy the structure, not the conclusions |

## 6. How this repository does it

This repo is the first user of its own rules:

- **Adoption record** = [ADR-0004](../docs/adr/0004-all-changes-via-pr.md) (gates and PR flow)
  plus [ADR-0003](../docs/adr/0003-why-this-repo-delays-admin-enforcement.md) (a superseded decision, kept for history);
- **Enforcement points** = four branch-protection settings + four CI jobs + `permissions.deny` in `.claude/settings.json`;
- **Not adopted**: approvals ≥ 1 (solo maintainer; required checks cover the gap instead) — which also means
  `Require review from Code Owners` has no effect today;
- **Adopted but currently inert**: `CODE_OF_CONDUCT.md` (only meaningful once there are outside contributors).

Self-check against rule 2 of §0: **every "adopted" here has an enforcement point** — you can use that same check on any
repository that claims to have adopted this spec.
