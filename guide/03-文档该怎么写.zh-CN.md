# 03 · 文档该怎么写

**[English](03-文档该怎么写.md)** · 简体中文

> 这一章讲**写法**，不讲"必须有"（那是 01、02 章的事）。
> 全章只有一条总判据，后面每个文件都用它检查：

> **文档的每一行，都要能回答"读者读完这一行，下一步做什么"。**
> 回答不了的句子，删掉。

---

## 0. 先分清读者，再动笔

同一个仓库里，文档的读者不是"所有人"，而是分层的。写之前先确定这一篇是给谁的：

| 读者 | 他怎么读 | 能容忍的长度 | 读到后要能做什么 |
|---|---|---|---|
| 陌生人 | 只看 README 前 20 行 | 很短 | 判断"要不要用"、"怎么跑起来" |
| 使用者 | 查 docs、CHANGELOG | 中等 | 找到某个具体用法 / 某个版本改了什么 |
| 贡献者 | 读 CONTRIBUTING + PR 模板 | 中等 | 知道怎么提、提完会发生什么 |
| **agent** | **每次会话全文加载 AGENTS.md** | **严格（≤200 行）** | 知道命令、边界、坑 |
| 未来的维护者 | 翻 ADR、git log | 不限 | 知道"为什么当时不是另一种" |

两个直接结论：

1. **同一份内容不要写给两个读者。** README 里塞 agent 指令，人看着是噪音，agent 也读不到（它不加载 README）。
2. **agent 是唯一一个"每次都会完整读一遍"的读者**，所以它的文档要按"上下文预算"来写，不按"完备"来写。

## 1. README.md

### 目的

让一个陌生人在 **5 分钟**内做出两个判断：**要不要用**、**怎么跑起来**。

### 骨架

```markdown
# 项目名

一句话：给谁、解决什么问题、和替代品的差别。

## 快速开始
<能直接复制粘贴、复制完就能跑的三五行>

## 它做什么 / 不做什么
- ✅ …
- ❌ …

## 文档
- 用法 → docs/
- 架构与决策 → docs/architecture/ · docs/adr/
- 贡献 → CONTRIBUTING.md
- 安全 → SECURITY.md（不要开公开 issue）

## 许可
MIT / Apache-2.0
```

### 写法要点

- **第一行写"给谁解决什么"，不写"是什么技术"。** 读者关心自己的问题，不关心你用了什么框架。
- **快速开始必须是"可复制粘贴并真的能跑"的命令。** 每次改依赖、改入口都回来验一遍——命令腐烂比代码腐烂更常见，因为没人编译它。
- **"不做什么"比"做什么"更能建立信任。** 明确排除项，能挡掉一半误用。
- **不写架构。** 架构放 `docs/architecture/`，README 只放一个链接。
- **徽章最多 3 个**，且每个都要有信息量（构建状态、版本、协议）。徽章墙说明作者更在意观感。

### 反例 → 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| "本系统采用微服务架构，基于 Spring Cloud…" | 这是实现，不是定位 | "给 5 人以内的团队做内部工单流转；不需要账号体系" |
| "简单易用、功能强大" | 形容词无信息量 | "一条命令起本地环境：`docker compose up`" |
| 三步安装，第二步写"配置好环境" | 读者卡在这里 | 列出确切的 `.env` 键与示例值 |
| 把 CHANGELOG 抄进 README | 双份维护，必然不同步 | 只留链接 |

### 判据（怎么算写对了）

1. 一个没用过这个项目的人，照着 README 能不能跑起来？让他试，不要自己试。
2. 把"它做什么/不做什么"两节删掉，读者还能不能判断适用性？不能，说明定位没写清。
3. README 超过 100 行了吗？超了就该往 `docs/` 搬。

**可以裁减**：私有的一次性脚本仓库，README 写清"跑什么、输出在哪"即可，不需要"不做什么"和许可。

## 2. AGENTS.md

### 目的

给 agent 一份**每次会话都会全文加载**的事实源：命令是什么、目录怎么分布、哪些不能碰、哪里有坑。

它是这个时代唯一"真正会被逐字读"的文档，所以写法和其他文档相反：**不求完备，只求会被用到。**

### 骨架（六段，顺序别乱）

```markdown
# AGENTS.md

## 项目是什么
2–3 行。只写 agent 无法从代码推断的定位与边界。

## 命令（唯一权威，勿自行发明）
| 用途 | 命令 | 备注（失败时的常见原因） |
|---|---|---|
| 测试 | `pnpm test` | 首次需先 `pnpm build` |

## 目录地图
- `src/api/` — HTTP 层，只做校验与转发
- `src/core/` — 领域逻辑，禁止反向依赖 api

## 硬约定
- 提交信息：Conventional Commits，关联 issue
- 新依赖：说明理由 + 评估维护状态

## 禁区（由 hooks / CI 强制）
- 不改 `prod/`、`.github/workflows/`
- 不读 `.env*`、`secrets/`

## 已知的坑
- Windows 上跑测试前必须先 build
- 不要用 `moment`，项目统一 `date-fns`

## 拿不准时
停下来问，列 2–3 个选项与取舍，不要猜。
```

### 写法要点

- **命令表是最高价值的一节。** 每条后面跟"失败时的常见原因"，比写十条代码风格有用十倍。agent 不会因为"注意风格"变好，但会因为"先 build 再 test"少踩一次坑。
- **每条约定都要可验证。** 写"用 2 空格缩进"，不写"注意代码风格"；写"提交信息带 issue 号"，不写"规范提交"。
- **"已知的坑"要持续追加。** 每踩一次坑加一条，这是全文档投入产出比最高的部分。
- **禁区要写清"为什么"和"怎么办"。** 只写"禁止修改 X"，agent 会绕；写"X 由人工 PR 处理，因为…"，它才会停。
- **只写"每次都要"的。** 模块级规则放子目录的 `AGENTS.md`，多步流程放 skill——两者都不该占这 200 行。
- **单文件 ≤200 行。** 超了不是"内容多"，是"位置错"。

### 反例 → 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| 把 README 复制一遍 | 浪费预算，且会不同步 | 第一行写"人类入口见 README" |
| "遵循项目既有风格" | 无判据 | "新增文件用 kebab-case，导出统一放 index.ts" |
| 列了 12 条代码规范 | 占了 1/3 预算，几乎不被用到 | 压成 3 条真正会踩的 |
| "不要破坏现有功能" | 无法执行 | "改 `src/api/` 后必须跑 `pnpm test:e2e`" |
| 写"如何发布"的 8 个步骤 | 属于流程，不是事实 | 移进 `.claude/skills/release/SKILL.md` |

### 一个值得抄的先例

GitHub 自家 `cli/cli` 的 `AGENTS.md` 里，最显眼的不是代码规范，而是三条**边界**：

- 不许给未经邀请的上游 PR 做准备（要 `help wanted` + 明确的验收标准，`core` 标签不动）；
- 安全问题不许进公开 issue / PR / commit；
- **"实现完了"不等于可以 commit、push、publish。**

这三条都不是"怎么写代码"，而是"什么时候该停"。**agent 文档里最贵的不是知识，是停止条件。**

### 判据

1. 把命令表里的每条命令照抄执行，能不能跑通？（跑不通就说明它已经腐烂）
2. agent 读完，知不知道"哪里不能碰、碰了会发生什么"？
3. 行数 ≤200？超出部分是不是该分层？

**可以裁减**：单人小项目可以只留"命令 + 禁区"两段；`目录地图` 在单文件项目里没用。

## 3. CLAUDE.md（如果存在）

### 目的

只放 Claude Code 专属的那一点点。**它不是第二份 AGENTS.md。**

### 写法

```markdown
@AGENTS.md

## Claude Code 专属
- 改 `src/billing/` 前先用 plan mode。
- 大范围搜索用 subagent，别在主上下文读 `dist/`。
```

- 第一行 `@AGENTS.md` 导入事实源，其余 ≤40 行。
- 只在"这条对别的工具没意义"时才写进这里（例如 plan mode、subagent 用法）。
- **Windows 团队不要用 symlink**（`core.symlinks` 关闭时 checkout 出来是一行文本文件），用 `@` 导入。

### 反例

- 把 AGENTS.md 内容复制一份 → 双事实源，改一处必漏一处，agent 随机选一个生效。
- 把 Claude 专属规则写进 AGENTS.md → 别的工具读到会困惑。

**可以裁减**：只用 Claude Code 一个工具、且不介意改名，可以只要 `AGENTS.md`，不要 `CLAUDE.md`。

## 4. CODEOWNERS

### 目的

把"谁来评审"从口头约定变成平台的自动指派。它是 agent 提交的第一道人工闸门——**前提是分支保护里开了 `Require review from Code Owners`，否则这个文件完全不生效。**

### 写法

```
# 默认责任人（必须是人类账号/团队，不能是 bot 或 agent）
*                       @org/maintainers

# 治理面：agent 不得自行修改
/.claude/               @org/agent-ops
/.github/workflows/     @org/agent-ops
/AGENTS.md              @org/agent-ops

# 文档
/docs/                  @org/docs-owners

# 关键业务
/src/billing/           @org/billing-owner
```

### 写法要点

- **从宽到窄排列**，后匹配的规则优先——所以把"治理面"放在 `*` 之后。
- **owner 必须是人。** 写 `@dependabot` 或写 agent 的账号，等于没有评审。
- **一定要在分支保护里勾上对应开关**，并在 README 或 CONTRIBUTING 里写一句"已开启"，否则下一个人会以为是装饰。
- 团队不存在时 GitHub 会静默忽略该行——改完去仓库首页确认 CODEOWNERS 没报错。

### 反例

- 全仓库只有一行 `* @me`：等于"所有事都归我"，实际是**没有路由**。
- 写了 CODEOWNERS 但没开开关：看起来有治理，实际零效果。

## 5. ADR（架构决策记录）

### 目的

回答**"为什么不是另一种做法"**。没有 ADR 的仓库，agent 会每隔几个月把同一批设计重做一遍——它只看到现状，看不到被否决的选项。

### 写法

```markdown
# ADR-0007：列表接口改用 cursor 分页

- 状态：Accepted            （Proposed / Accepted / Superseded by ADR-00XX）
- 日期：2026-11-16
- 决策者：@alice、agent: claude-code（提案）

## 背景
现状是什么，为什么这个决定现在必须做。

## 选项
1. 保留 page/size —— 改动最小，但重复/漏项问题不消失。
2. cursor（keyset）—— 稳定；需一次改 4 个端点，旧参数保留 2 个版本。
3. 快照分页 —— 一致性最好；需服务端存游标，运维成本高。

## 结论
选 2。理由：一致性与成本最优，兼容期足够长。

## 后果
- 正面：分页稳定；深翻页变快。
- 负面：无法跳页；`total` 只在首页返回，前端要改。
- 迁移：`page/size` 保留到 v3.0。
```

### 写法要点

- **一个 ADR 只记一个决定。** 塞三个决定的 ADR，半年后没人能引用。
- **选项必须写"为什么不选"。** 只写结论的 ADR 等于没有 ADR。
- **后果要诚实写代价。** 只写优点的 ADR 是宣传，不是记录。
- **永不删除，只标 Superseded。** 决策的历史价值在于"当时为什么这么想"。
- 文件名 `NNNN-短横线标题.md`，四位递增，方便交叉引用。

### 反例

- 写成会议纪要（谁说了什么），而不是决策（选了什么、为什么）。
- 事后补一条 ADR 编造理由——比没有更糟，会误导后来者。

## 6. PR 模板

### 目的

让评审者**在不追问的情况下**拿到判断所需的信息。对 agent 提交尤其重要：它的 PR 往往"看起来都对"，风险藏在没说的部分。

### 骨架

```markdown
## 改了什么
一句话 + 2–5 条要点。

## 为什么
Closes #123

## 影响面
- [ ] 公共 API / 数据格式变更（→ 更新 CHANGELOG + 文档）
- [ ] 新依赖（→ 说明理由）
- [ ] 数据库迁移（→ 附回滚脚本）

## 怎么验证的
<贴真实命令与输出，不要写"已测试">

## 自检
- [ ] 未触碰禁区
- [ ] 行为变更已更新 CHANGELOG
- [ ] 架构/选型变更已补 ADR

## 需要 reviewer 特别看的地方
<明说"我不确定的部分">
```

### 写法要点

- **"怎么验证的"必须贴输出。** 没有输出的"已测试"等于没测。
- **"需要 reviewer 特别看的地方"是最值钱的一节。** 它把 reviewer 的注意力从"通读 diff"变成"重点核对三处"。
- 勾选项控制在 5 条以内。勾 12 项的结果是全部乱勾。
- 影响面用**复选框**而不是散文——它决定了 reviewer 要不要去查 CHANGELOG。

### 反例

- 只有一句"fix bug"。
- 模板很长，但没有任何一栏要求证据。

## 7. CHANGELOG.md

### 目的

它是**使用者与 agent 判断"这个版本能不能用"的第一手依据**，也是唯一记录"行为变了"的地方。git log 不是 CHANGELOG：log 记录过程，CHANGELOG 记录结果。

### 写法

```markdown
## [Unreleased]

## [2.4.0] - 2026-11-16

### Added
- 列表接口支持 cursor 分页（`cursor` / `limit`），旧 `page` 参数保留兼容 (#456)

### Changed
- 错误响应统一为 `{ code, message, requestId }` (#461)

### Fixed
- 修复并发写入偶发重复索引 (#470)

### Security
- 升级 `undici` 修复请求走私风险 (#472)
```

### 写法要点

- **只写用户可感知的变化**，不写内部重构（"重命名变量"不是变更）。
- **每条带 PR 号**，讨论能回溯。
- **破坏性变更单独成节**，并在 README 顶部提示迁移路径。
- 版本号走 semver；"Changed"里出现不兼容改动，就该是 major。
- 顶部留 `## [Unreleased]`，让人有地方写。

### 反例

- 把 `git log --oneline` 直接贴进来（那是过程，不是结果）。
- 半年不更新，发布时一次性补——必然漏掉最关键的破坏性变更。

## 8. SECURITY.md 与 CONTRIBUTING.md

这两份是**写给人看的**（agent 不会自动加载它们），所以重点是"人能不能一眼找到正确路径"。

### SECURITY.md

必须有：**支持哪些版本**、**私密上报通道**、**响应时限**。

```markdown
## 支持的版本
只对最新 minor 提供修复。

## 上报
用仓库 Security 页的 "Report a vulnerability"，**不要开公开 issue**。
3 个工作日内确认，10 个工作日内给出评估结论。
```

- 引导走公开 issue 等于没有安全策略。
- 写具体天数，不写"尽快"。

### CONTRIBUTING.md

必须有：**分支模型**、**提交格式**、**PR 流程**、**评审 SLA（写数字）**。

- "尽快回复"= 没有承诺；"3 个工作日内首次回应"才是承诺。
- 如果详细内容放在 `contributing/` 目录或 `docs/`，**根目录或 `.github/` 下仍要有一个入口文件**指过去——GitHub 只认固定位置的那个文件，`contributing/` 目录本身不算。

> 关于 agent：它不会自动读 CONTRIBUTING。要让它遵守，办法是在 `AGENTS.md` 里写一句指针，
> 例如 `cli/cli` 的做法：`Read CONTRIBUTING, the canonical contribution policy.`
> 这样"路径存在"就成了一个可自查的事实。

## 9. docs/ 与 docs/index.md

- `docs/index.md` 是**地图**，不是散文：按"教程 / 参考 / 架构 / ADR / 运维"分类给入口。
- 一个文件一个主题，文件名即主题。
- 长内容不进 README，README 只放"30 秒能得到什么"。
- 文档里的路径必须真实存在——重构后失效的链接，是 agent 照着错路干活的头号原因。

## 10. 跨文件的通用写法

| 原则 | 具体做法 |
|---|---|
| **具体化取代形容词** | "快速"→"3 秒内返回"；"易用"→"一条命令" |
| **命令取代描述** | 不写"需要初始化数据库"，写 `docker compose up -d pg` |
| **例子取代规则** | 一条正例 + 一条反例，胜过三条抽象要求 |
| **写现状，不写将来** | "将会支持"→ 写进 issue，不进文档 |
| **长度预算** | README ≤100 行；AGENTS ≤200 行；ADR ≤80 行；超出就拆 |
| **可验证** | 每条要求都要能被"照做一遍"检验；不能检验的改成例子 |
| **路径必须真实** | 引用其他文件时用相对路径，重构时一起改 |
| **一份内容一个位置** | 别在两处维护同一份事实；要复用就链接 |

---

## 11. 写完自检（10 条）

- [ ] README 的前 20 行，能让陌生人判断"要不要用"吗？
- [ ] 快速开始的命令，最后一次**实际跑通**是什么时候？
- [ ] AGENTS.md 里每条命令都能照抄执行吗？失败原因写了吗？
- [ ] AGENTS.md 有"禁区"和"停止条件"吗（什么时候该问人）？
- [ ] 禁区写的"为什么"，够不够让 agent 不去绕？
- [ ] ADR 的"选项"里写了"为什么不选"吗？
- [ ] PR 模板有"怎么验证的"和"需要特别看的地方"两栏吗？
- [ ] CHANGELOG 的最近一条，是用户可感知的变化还是内部重构？
- [ ] CODEOWNERS 的 owner 是人类账号吗？分支保护开关开了吗？
- [ ] 文档里引用的路径，现在还存在吗？

## 附：本章对应的自查项

本章是写法指导，不对应"必须有"的判定。若想自动化检查，可参考：

| 自查项 | 检查什么 |
|---|---|
| `R030`–`R033` | AGENTS.md / CLAUDE.md 的长度与结构 |
| `R037` | AGENTS.md 引用的路径是否还存在 |
| `R038` | ADR 文件名是否符合 `NNNN-` |
| `R039` | PR 模板是否含自检清单 |
| `R027` | LICENSE / 关键文件是否还是占位文本 |

其余（"写得好不好"）**无法自动判**，只能靠本章的判据人工核对——这是刻意的：
**能自动判的只是"有没有做"，"写得对不对"永远需要一个读者。**
