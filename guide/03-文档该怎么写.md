# 03 · How to write each document

**English** · [简体中文](03-文档该怎么写.zh-CN.md)

> This chapter is about **how to write**, not "what must exist" (that's chapters 01 and 02).
> It has one criterion, applied to every file below:
>
> Generic terms for tool mechanisms are used throughout; their mapping to concrete file names lives in the
> [mechanism map](../spec/mechanism-map.md) (appendix, non-normative).

> **Every line must answer: what does the reader do next?**
> If a sentence can't answer that, delete it.

---

## 0. Know the reader before you write

Documents in one repository do not have "everyone" as their reader. Decide first:

| Reader | How they read | Length tolerance | What they must be able to do afterwards |
|---|---|---|---|
| A stranger | first 20 lines of the README | very short | decide whether to use it, and run it |
| A user | looks up `docs/`, `CHANGELOG` | medium | find a specific usage / see what changed in a version |
| A contributor | reads CONTRIBUTING + the PR template | medium | know how to submit, and what happens next |
| **An agent** | **loads the whole `AGENTS.md` every session** | **strict (≤200 lines)** | know the commands, the boundaries, the pitfalls |
| A future maintainer | reads ADRs and `git log` | unlimited | know "why not the alternative" |

Two consequences:

1. **Don't write the same content for two readers.** Agent instructions inside the README are noise for humans and
   invisible to the agent (it does not load the README).
2. **The agent is the only reader that reads the whole file every time**, so its documents are written to a
   **context budget**, not to completeness.

---

## 1. README.md

### Purpose

Let a stranger decide, within **five minutes**: *should I use this*, and *how do I run it*.

### Skeleton

````markdown
# Project name

One sentence: for whom, solving what, and how it differs from the alternative.

## Quick start
<three to five lines that can be pasted and actually run>

## What it does / what it does not
- ✅ …
- ❌ …

## Docs
- Usage → docs/
- Architecture and decisions → docs/architecture/ · docs/adr/
- Contributing → CONTRIBUTING.md
- Security → SECURITY.md (please do not open a public issue)

## License
MIT / Apache-2.0
````

### Writing rules

- **The first line says who it is for, not what stack it uses.** Readers care about their problem, not your framework.
- **Quick start must be paste-and-run.** Re-check it every time dependencies or entry points change — command rot is
  more common than code rot, because nothing compiles a command.
- **"What it does not do" builds more trust than "what it does".** It filters out half of the misuse.
- **No architecture here.** Architecture goes to `docs/architecture/`; the README gets a link.
- **At most three badges**, each carrying information (build status, version, licence). A wall of badges tells the
  reader the author cares more about appearance.

### Counter-examples → better

| Counter-example | Problem | Better |
|---|---|---|
| "This system adopts a microservice architecture based on Spring Cloud…" | implementation, not positioning | "Turns tickets into a flow for teams of ≤5; no account system needed" |
| "Simple, easy, powerful" | adjectives carry no information | "One command boots the local stack: `docker compose up`" |
| Three install steps, the second being "configure the environment" | the reader is stuck here | list the exact `.env` keys and example values |
| Copying the CHANGELOG into the README | two copies, guaranteed to diverge | a link only |

### Criteria

1. Can someone who has never used it get it running from the README alone? Have *them* try, not you.
2. Delete the "does / does not" section — can the reader still judge fit? If not, positioning is missing.
3. Is it over 100 lines? Then content belongs in `docs/`.

**Can be dropped**: a private one-off script repo only needs "what to run, where the output goes".

## 2. AGENTS.md

### Purpose

A source of truth for the agent that is **loaded in full every session**: which commands exist, how the tree is laid
out, what must not be touched, where the traps are.

It is the only document in this era that is genuinely read word by word — so it is written the opposite way from
everything else: **not for completeness, for being used.**

### Skeleton (eight sections, keep the order)

````markdown
# AGENTS.md

## What this project is
2–3 lines. Only what an agent cannot infer from the code.

## Language
- My language is <your language>. Talk to me, write docs, lists and reports in it.
- Do not translate: rule IDs, file paths, commands, code identifiers.
- When a translation conflicts with the source, the source wins — and say where they differ.

## Commands (single source of truth — do not invent your own)
| Purpose | Command | Notes (common failure) |
|---|---|---|
| Test | `pnpm test` | needs `pnpm build` first |

## Directory map
- `src/api/` — HTTP layer, validation and forwarding only
- `src/core/` — domain logic; must not import from api

## Hard rules
- Commits: Conventional Commits, reference the issue
- New dependency: state the reason and assess maintenance status

## Forbidden (enforced by hooks / CI)
- Do not modify `prod/`, `.github/workflows/`
- Do not read `.env*`, `secrets/`

## Known pitfalls
- On Windows, build before running tests
- Do not use `moment`; the project uses `date-fns`

## When unsure
Stop and ask. Present 2–3 options with trade-offs; do not guess.
````

### Writing rules

- **The command table is the highest-value section.** Pair each command with *why it usually fails* — that is worth
  ten style guidelines. Agents don't get better because you wrote "mind the style"; they get better because you wrote
  "build before test".
- **Every rule must be checkable.** "Two-space indentation", not "mind the formatting"; "reference the issue in the
  commit", not "follow commit conventions".
- **Keep appending to "known pitfalls".** One line per incident; this is the best return on effort in the whole file.
- **State why a forbidden area is forbidden, and what to do instead.** "Do not touch X" invites workarounds;
  "X is handled by a human PR because …" makes the agent stop.
- **Only what is needed every session.** Per-module rules go into the subdirectory's own `AGENTS.md`; multi-step
  procedures go into a skill. Neither belongs in these 200 lines.
- **≤200 lines per file.** Going over does not mean "more content", it means "wrong location".
- **Declare the output language once, near the top.** Without it the agent follows the code comments or whatever it wrote last time, and one repository ends up with two languages. Copy-paste ready: [templates/prompt-locale.md.tmpl](../templates/prompt-locale.md.tmpl).

### Counter-examples → better

| Counter-example | Problem | Better |
|---|---|---|
| Copying the README | wastes budget and diverges | first line: "human entry point: README" |
| "Follow the existing code style" | no criterion | "new files use kebab-case; re-exports live in index.ts" |
| Twelve style rules | a third of the budget, almost never used | compress to three that actually bite |
| "Do not break existing functionality" | not actionable | "after touching `src/api/`, run `pnpm test:e2e`" |
| Eight steps for releasing | that's a procedure, not a fact | move it into a release skill in the tool-specific asset directory |

### Language

**Declare the output language once, near the top.** Without it the agent follows the code comments or whatever it
wrote last time, and one repository ends up with two languages. Copy-paste ready:
[templates/prompt-locale.md.tmpl](../templates/prompt-locale.md.tmpl).

Pin the "do not translate" list: rule IDs, paths, commands, code identifiers — the first translation otherwise loses
the checklist IDs.

### A precedent worth copying

The most prominent part of GitHub's own `cli/cli` `AGENTS.md` is not code style but three **boundaries**:

- Do not prepare an unsolicited upstream PR (it needs `help wanted` **and** explicit acceptance criteria; the `core`
  label means hands off);
- Security issues must not enter public issues / PRs / commits;
- **"Implementation complete" does not mean you may commit, push, or publish.**

None of these is about writing code — they are about **when to stop**.

**The most valuable content in an agent document is not knowledge. It is stop conditions.**

### Criteria

1. Paste every command from the table into a shell — does each one run? (If not, it has already rotted.)
2. After reading, does the agent know what it must not touch, and what happens if it does?
3. Is it ≤200 lines? Is the overflow content that should be layered elsewhere?

**Can be dropped**: a single-author, single-purpose project can keep just "commands" and "forbidden".

## 3. The tool-specific instruction file (if you have one)

### Purpose

Only the handful of lines that are specific to one tool. **It is not a second AGENTS.md.**

### How

```markdown
@AGENTS.md

## Specifics of your tool
- Use plan mode before touching `src/billing/`.
- Use a subagent for broad searches; don't read `dist/` in the main context.
```

- Start with `@AGENTS.md`, keep the rest ≤40 lines.
- Only write here what is meaningless to other tools (plan mode, subagent usage).
- **Windows teams: do not use a symlink** (`core.symlinks` off checks out a one-line text file); use the `@` import.

### Counter-examples

- Duplicating AGENTS.md → two sources of truth, one will be missed, the agent picks one at random.
- Putting tool-specific rules into AGENTS.md → confuses every other tool.

**Can be dropped**: if one tool is the only one you use, you can keep just `AGENTS.md`.

## 4. CODEOWNERS

### Purpose

Turn "who reviews this" from a verbal agreement into automatic assignment. It is the first human gate for agent
commits — **but only if branch protection has `Require review from Code Owners` turned on. Otherwise the file does nothing.**

### How

```
# Default owners (must be human accounts/teams — never a bot or an agent)
*                       @org/maintainers

# Governance surface: agents must not change these on their own
/<tool asset dir>/      @org/agent-ops
/.github/workflows/     @org/agent-ops
/AGENTS.md              @org/agent-ops

# Docs
/docs/                  @org/docs-owners

# Critical business areas
/src/billing/           @org/billing-owner
```

### Rules

- **Order from broad to narrow**; the last match wins — that's why the governance entries sit below `*`.
- **Owners must be people.** `@dependabot` or an agent account means no review happens.
- **Turn the branch-protection toggle on** and say so in the README or CONTRIBUTING — otherwise the next person assumes
  it is decoration.
- A non-existent team is silently ignored; check the repository page after editing.

### Counter-examples

- A single line `* @me`: everything is "owned" by one person, which in practice means **no routing at all**.
- CODEOWNERS written, toggle never enabled: looks like governance, does nothing.

## 5. ADR (architecture decision record)

### Purpose

Answer **"why not the alternative"**. Without ADRs, an agent re-derives the same designs every few months — it sees the
current state, not the options that were rejected.

### How

```markdown
# ADR-0007: switch the list endpoint to keyset pagination

- Status: Accepted            (Proposed / Accepted / Superseded by ADR-00XX)
- Date: 2026-11-16
- Deciders: @alice, agent: <your tool> (proposal)

## Context
What is true today, and why this decision cannot be postponed.

## Options
1. Keep page/size — smallest change; duplicates and gaps remain.
2. Keyset pagination — stable; four endpoints to change; legacy params kept for two releases.
3. Snapshot pagination — best consistency; server-side cursors, higher ops cost.

## Decision
Option 2. Rationale: best consistency/cost ratio; the compatibility window is long enough.

## Consequences
- Positive: stable pagination; deep pages get faster.
- Negative: no jump-to-page; `total` only on the first page, the frontend must change.
- Migration: `page/size` kept until v3.0.
```

### Rules

- **One decision per ADR.** An ADR that holds three decisions cannot be cited later.
- **Options must include why they were rejected.** An ADR with only a conclusion is not an ADR.
- **Consequences must include the cost.** Only listing benefits makes it marketing, not a record.
- **Never delete; mark Superseded.** The value is in "what we thought at the time".
- File name `NNNN-kebab-title.md`, four digits, incrementing — so it can be cross-referenced.

### Counter-examples

- Meeting minutes (who said what) instead of a decision (what was chosen, and why).
- Writing an ADR after the fact with an invented rationale — worse than having none.

## 6. Pull-request template

### Purpose

Give the reviewer **everything needed to judge, without asking follow-ups**. This matters most for agent PRs, which
often "look correct" while the risk hides in what they didn't say.

### Skeleton

````markdown
## What changed
One sentence + 2–5 bullets.

## Why
Closes #123

## Impact
- [ ] Public API / data format change (→ update CHANGELOG + docs)
- [ ] New dependency (→ justify it)
- [ ] Database migration (→ include the rollback script)

## How it was verified
<paste the real command and its output; "tested" is not evidence>

## Self-check
- [ ] Forbidden areas untouched
- [ ] Behaviour change recorded in CHANGELOG
- [ ] Architecture/selection change recorded in an ADR

## What the reviewer should look at closely
<say plainly which parts you are unsure about>
````

### Rules

- **"How it was verified" must contain output.** "Tested" is worth nothing.
- **"What the reviewer should look at closely" is the most valuable section** — it turns review from "read the whole
  diff" into "check these three things".
- Keep the checklist under five items. Twelve items means everything gets ticked blindly.
- Use checkboxes for impact, not prose — it decides whether the reviewer opens the CHANGELOG.

### Counter-examples

- A single line: "fix bug".
- A long template where no section demands evidence.

## 7. CHANGELOG.md

### Purpose

The first-hand source for users **and agents** deciding "can I upgrade?". It is also the only place that records
"behaviour changed". `git log` is not a changelog: the log records the process, the changelog records the result.

### How

```markdown
## [Unreleased]

## [2.4.0] - 2026-11-16

### Added
- Keyset pagination on list endpoints (`cursor` / `limit`); legacy `page` kept (#456)

### Changed
- Error responses unified as `{ code, message, requestId }` (#461)

### Fixed
- Duplicate indexes under concurrent writes (#470)

### Security
- Bumped `undici`, fixing request-smuggling exposure (#472)
```

### Rules

- **Only user-visible changes.** Internal refactors ("renamed a variable") are not changes.
- **Every entry carries the PR number** so the discussion is traceable.
- **Breaking changes get their own section**, plus a migration note at the top of the README.
- Follow semver; an incompatible entry under "Changed" means the release is a major.
- Keep `## [Unreleased]` at the top so there is always somewhere to write.

### Counter-examples

- Pasting `git log --oneline` (process, not result).
- Updating it once every six months — the breaking change will be missing.

## 8. SECURITY.md and CONTRIBUTING.md

Both are written for **humans** (agents do not load them automatically), so the point is that a person finds the right
path immediately.

### SECURITY.md

Must say: **which versions are supported**, **where to report privately**, **how fast you respond**.

```markdown
## Supported versions
Only the latest minor gets fixes.

## Reporting
Use the Security tab → "Report a vulnerability". **Do not open a public issue.**
We acknowledge within 3 business days and give an assessment within 10.
```

- Pointing people at public issues means you have no security policy.
- Give concrete numbers, not "as soon as possible".

### CONTRIBUTING.md

Must say: **branching model**, **commit format**, **PR flow**, **review SLA (a number)**.

- "We'll respond soon" is not a commitment; "first response within 3 business days" is.
- If the detail lives in a `contributing/` directory or in `docs/`, **keep an entry file at the repo root or under
  `.github/`** pointing at it — GitHub only recognises the fixed locations, and a `contributing/` directory alone does
  not count.

> About agents: they will not read CONTRIBUTING on their own. To make them follow it, put a pointer in `AGENTS.md`,
> the way `cli/cli` does: `Read CONTRIBUTING, the canonical contribution policy.`
> Then "the path exists" becomes something a checker can verify.

## 9. docs/ and docs/index.md

- `docs/index.md` is a **map**, not an essay: entry points grouped as tutorial / reference / architecture / ADR / operations.
- One topic per file; the file name is the topic.
- Long content does not go into the README; the README only carries "what you get in 30 seconds".
- Paths in docs must actually exist — dead links after a refactor are the number-one cause of an agent walking the
  wrong path.

---

## 10. Cross-cutting rules

| Principle | In practice |
|---|---|
| **Concrete beats adjectives** | "fast" → "returns in 3 s"; "easy" → "one command" |
| **Commands beat descriptions** | not "initialise the database" but `docker compose up -d pg` |
| **Examples beat rules** | one good example + one counter-example beats three abstract requirements |
| **Write the present, not the future** | "will support" → put it in an issue, not in a doc |
| **Length budget** | README ≤100 lines; AGENTS ≤200; ADR ≤80; split when you exceed |
| **Checkable** | every requirement must survive "follow it once"; if not, turn it into an example |
| **Paths must be real** | use relative links; update them in the same commit as the refactor |
| **One fact, one place** | never maintain the same fact twice; link instead |

## 11. Self-check after writing (10 items)

- [ ] Do the first 20 lines of the README let a stranger judge whether to use it?
- [ ] When was the quick-start command **last actually run**?
- [ ] Can every command in AGENTS.md be pasted and run? Are the failure notes there?
- [ ] Does AGENTS.md have "forbidden areas" and "stop conditions" (when to ask a human)?
- [ ] Are the reasons behind the forbidden areas strong enough that an agent won't work around them?
- [ ] Does the ADR's "options" section say why each alternative was rejected?
- [ ] Does the PR template ask "how it was verified" and "what to look at closely"?
- [ ] Is the latest CHANGELOG entry a user-visible change, or an internal refactor?
- [ ] Are the CODEOWNERS owners human accounts? Is the branch-protection toggle on?
- [ ] Do the paths referenced in the docs still exist?

## Appendix: which checks correspond to this chapter

This chapter is about *how to write*; it does not decide what must exist. If you want automation, these are the closest
checks:

| Check | What it verifies |
|---|---|
| `R030`–`R033` | length and structure of `AGENTS.md` and of the tool-specific instruction file |
| `R037` | whether paths referenced from AGENTS.md still exist |
| `R038` | ADR file names follow `NNNN-` |
| `R039` | the PR template contains a self-check list |
| `R027` | LICENSE and other key files are not placeholders |

Everything else — "is it written well" — **cannot be automated**, only reviewed against the criteria above.
That is deliberate: **a checker can only see "is it there"; "is it right" always needs a reader.**
