# 06 · 信息该放哪：立项、状态与待办

> 这一章只回答一件事：**某条信息应该放在哪种媒介里。**
> 覆盖两个时间点：**立项时**（范围、顺序、进度）与**运行中**（状态、待办、换会话接手）。

---

## 0. 一条判据：变化速度决定载体

| 信息 | 变化速度 | 载体 |
|---|---|---|
| 事实（命令、目录、禁区、坑） | 慢 | `AGENTS.md` |
| 决策（为什么不是另一种） | 极慢 | `docs/adr/` |
| **范围（做什么、不做什么、怎么算完成）** | **一次定，靠变更记录** | **`docs/spec/` 一份** |
| 变更（用户可感知的行为） | 每次发布 | `CHANGELOG.md` |
| **顺序（先做哪块）** | 会调整 | **milestone（批次）** |
| **状态（做到哪 / 下一步）** | 每次会话 | **PR 描述；有 issue 时以 issue 为准** |
| **进度（做没做完）** | 实时 | **issue 的 open/closed** |

一句话：**慢变写文件，快变交给平台，中间态写进 PR。**

判断一份东西该不该写成文档，只问一句：**它需要"状态流转"吗？**
需要（做没做、卡没卡）→ 交给 issue / milestone；不需要（读完就懂、答案稳定）→ 写成 md。

---

## 1. 立项期：范围、顺序、进度是三件事

立项时定好方案和功能，最容易犯的错是**把它们全塞进一份 `roadmap.md`**——而 roadmap 一旦同时背范围、顺序、进度，必然腐烂（进度是快变的）。

### 该有的两个载体

**① 范围基线：`docs/spec/0001-<项目名>.md`（一次性、慢变）**

```markdown
# 0001 — <项目名>

## 目标
一段话：做完之后，什么变成什么样。

## 功能清单
- F1 <一句话>（可被 issue 引用：见 #12）
- F2 …

## 非目标 ← 必填
- 不做 X（理由）
- 不做 Y（理由）

## 验收（可判定）
- [ ] …
- [ ] …

## 变更记录
- 2026-11-17 初版
- 2026-12-02 F3 移出范围（理由：…）
```

**刻意不写**：日期、百分比、"预计 Q3 完成"。这三样是腐烂源——第一次延期就全部失效，而且没人会回来改。

**② 顺序与进度：milestone + issue（平台原生）**

- 每个功能 = 一个 issue，正文引用 `F1`；
- 批次 = milestone（`v0.9` / `v1.0`），**用批次表达顺序，不用日期**；
- 进度 = issue 的 open/closed，天然有状态流转，不需要人维护百分比。

### 为什么不是 roadmap.md

实测十个头部仓库：`ROADMAP*` **0/10**、`STATUS|PROGRESS|PLAN*` **0/10**。
它们怎么做的：

| 仓库 | 做法 |
|---|---|
| `github/roadmap` | 整个仓库只有 README，**路线图就是那 211 个 issue** |
| `kubernetes/enhancements` | `keps/` 放编号提案（范围），进度看状态字段与 milestone |
| `rust-lang/rfcs` | `text/` 放编号 RFC（范围），实现进度在 issue |
| `microsoft/vscode` | 功能目录下的 `roadmap.md` + 每个 phase 一份 `phaseNN-plan.md`（有 `Status:` 字段） |

**共同点：范围是文档，顺序和进度是有状态的对象。**

### 什么时候确实需要一份"路线图文档"

| 情况 | 做法 |
|---|---|
| 对外有承诺（客户/社区） | 独立的 roadmap 仓库，条目用 issue，并明写"会变" |
| 多团队协同 | Project 视图 + milestone，**仍然不要手写 md 表格** |

### 变更控制的最小版

范围变了不需要开流程会，只需要两件事：**在 spec 的「变更记录」里记一行**；
若变更影响架构或对外契约，**补一条 ADR**。这样"当初定的"和"后来改的"都留得住。

## 2. 运行期：状态与待办

### 2.1 先承认：这个问题没有"纯文档解法"

工具侧机制只覆盖一部分：

| 机制 | 覆盖范围 | 覆盖不了 |
|---|---|---|
| 会话恢复（`--continue` / `--resume`） | 同一台机器上的同一个会话 | 换机器、换人、开新会话 |
| 自动记忆（`MEMORY.md` + 主题文件） | 同一台机器上跨会话 | 不进 git，换机器即失忆 |
| 子代理记忆（`memory: project`） | 可提交，跨机器 | 只服务那个子代理 |

而"写进仓库"这条路也不自动成立。本仓库自己就是反例：PR #3–#6 的描述各 163 字、
全是模板套话，打开中的 issue 0 个，提交只有标题。
结果：新会话能回答"**做了什么**"，回答不了"**下一步做什么**"。

**结论：状态必须落在一个"必然会存在"的载体上；靠记性维护的文档一定会忘。**

### 2.2 三种承载方式，按可靠性排

| 方式 | 可靠性 | 什么时候用 | 代价 |
|---|---|---|---|
| **A 靠记性写文档** | 低 | 不建议 | 会忘、会过期，而且会变成第二真相源 |
| **B 模板必填 + 评审** | 中 | 有人评审的仓库 | 漏写会被 review 挡住；没人看时失效 |
| **C 写进工具** | 高 | **已经有自动化发布路径** | 工具多一两个必填参数；离线/无令牌时用不了 |

方式 C 的意思是：把「下一步 / 非目标 / 怎么验证的」做成**发布流程的必填项**。
漏写的后果是**发不出去**，而不是文档静默过期——**这是唯一不依赖记性的强制点。**

### 2.3 推荐规则：按实际情况往下落

1. **已有自动化发布** → 选 **C**：发布参数里加"下一步（没有就显式写'无'）"和"非目标"，并在 PR 描述里结构化输出。
2. **只有手工 PR、但有评审** → 退到 **B**：PR 模板这三栏设为必填，评审者检查。
3. **单人、无评审** → B 的简化版：模板保留三栏，并在状态行写「**最近更新日期 + 依据 PR 号**」。
   它仍会过期，但**过期是可见的**：日期旧了一眼看得出，PR 号可点开核对。
4. **任何情况下都不要新建独立的状态文件**（`PROGRESS.md` / `STATUS.md` / `sessions/` 目录）：
   它们会与 PR 描述、issue 构成多个真相源。

### 2.4 据此不做的三件事

- ❌ **不建 `PROGRESS.md` / `STATUS.md` / `sessions/`**：多个真相源，且每个会话一个文件必然积累成噪音。
- ❌ **不让检查器判"状态是否新鲜"**：`mtime` 在 `clone` 之后**全部变成 clone 时间**，
  这条规则在 CI 和新机器上永远通过——测的是"你什么时候 clone 的"，不是"状态新不新鲜"。
- ❌ **不把待办清单写进 `AGENTS.md`**：挤占每次会话的上下文，而清单是最容易腐的东西。

### 2.5 接手判据

新会话**只读三样**，能回答**四个问题**：

| 读 | 答 |
|---|---|
| 最近 PR 的标题与描述 | 做到哪 |
| 打开中的 issue / PR | 下一步做什么 |
| `AGENTS.md` | 哪些不能碰、为什么是这样（需要时再看 ADR） |

再加一条纪律：**读完先跑一条命令对账**。文件说的状态可能已过期，能执行的东西才是真相。
