# 06 · Where information lives: planning, state, releases

**English** · [简体中文](06-信息该放哪.zh-CN.md)

> This chapter answers one question: **which medium should a given piece of information live in?**
> It covers two moments: **planning** (scope, order, progress) and **running** (state, to-dos, handing over).

---

## 0. One criterion: the rate of change decides the medium

| Information | Rate of change | Medium |
|---|---|---|
| Facts (commands, layout, forbidden areas, pitfalls) | slow | `AGENTS.md` |
| Decisions (why not the alternative) | very slow | `docs/adr/` |
| **Scope (what to build, what not to, definition of done)** | **decided once, then change-controlled** | **one file in `docs/spec/`** |
| Changes (user-visible behaviour) | every release | `CHANGELOG.md` |
| **Order (what comes first)** | adjusted occasionally | **milestones (batches)** |
| **State (where we are / what's next)** | every session | **the PR description; an issue wins if one exists** |
| **Progress (done or not)** | real time | **issue open/closed** |

One line: **slow-changing → a file; fast-changing → the platform; in-between → the PR.**

To decide whether something should be a document at all, ask one thing: **does it need state transitions?**
If yes (done/not done, blocked/unblocked) → an issue or milestone. If no (read once, answer is stable) → a markdown file.

## 1. Planning: scope, order and progress are three different things

The most common mistake at kickoff is stuffing all three into one `roadmap.md` — and once a roadmap carries scope,
order *and* progress, it rots, because progress changes constantly.

### Two carriers

**① Scope baseline: `docs/spec/0001-<project>.md` (written once, slow-changing)**

```markdown
# 0001 — <project name>

## Goal
One paragraph: after this is done, what is different.

## Features
- F1 <one line> (referenced by issues: see #12)
- F2 …

## Non-goals ← required
- Not doing X (why)
- Not doing Y (why)

## Definition of done (checkable)
- [ ] …
- [ ] …

## Change log
- 2026-11-17 initial
- 2026-12-02 F3 moved out of scope (why: …)
```

**Deliberately absent**: dates, percentages, "expected in Q3". Those are the rot sources — the first slip invalidates
them all, and nobody comes back to fix them.

**② Order and progress: milestones + issues (native to the platform)**

- one issue per feature, referencing `F1`;
- batches as milestones (`v0.9`, `v1.0`) — **express order as batches, not dates**;
- progress is issue open/closed: state transitions come for free, nobody maintains a percentage.

### Why not a `roadmap.md`

Measured across ten top repositories, **at the root**: `ROADMAP*` **0/10**, `STATUS|PROGRESS|PLAN*` **0/10**.
Note the scope — root directory only; some repos keep a roadmap inside a feature directory (`microsoft/vscode` below). What that shape has to solve is "the plan rotting next to the code", not "should a roadmap exist".
What they do instead:

| Repository | Approach |
|---|---|
| `github/roadmap` | the repo is a README plus **211 issues** — the roadmap *is* the issue list |
| `kubernetes/enhancements` | `keps/` holds numbered proposals (scope); progress lives in status fields and milestones |
| `rust-lang/rfcs` | `text/` holds numbered RFCs (scope); implementation progress lives in issues |
| `microsoft/vscode` | a `roadmap.md` inside the feature directory + one `phaseNN-plan.md` per phase (with a `Status:` field) |

**Common denominator: scope is a document; order and progress are objects with state.**

### When you do need a roadmap document

| Situation | Do |
|---|---|
| Public commitments (customers, community) | a standalone roadmap repository, entries as issues, with an explicit "this may change" |
| Multiple teams | a Project view + milestones — **still not a hand-written markdown table** |

### The minimal change control

Changing scope does not need a review board — it needs two things: **one line in the spec's change log**, and
**an ADR if it affects architecture or an external contract**. That keeps both "what we decided then" and
"what we changed later".

## 2. Releasing: when to release, and how to write a release

Three artefacts, don't mix them:

| Artefact | What it is | Does it change |
|---|---|---|
| **tag** | an immutable pointer (`v1.2.0`) | never |
| **GitHub Release** | the announcement for this version: what a user will notice | basically fixed after publication (errata allowed) |
| **CHANGELOG** | the cumulative record, grouped by version | appended with every release |

### 2.1 When to release (any one of these)

1. **Accumulated user-visible change**: `Unreleased` holds at least one Added / Changed / Fixed that is **not an
   internal refactor**;
2. **Security or data-correctness fix**: release immediately, don't wait for a batch;
3. **Platform/dependency change that breaks older versions**: a compatibility release.

**Do not release because**: there are a lot of commits, it's the end of the month, or you want a version number to exist.

### 2.2 Choosing the version number

Semantic versioning; the criterion is **whether a user has to change their code**, not how many lines changed:

| Change | Position |
|---|---|
| Breaking (callers must change) | major |
| New capability (works without changes) | minor |
| Bug fix / internal improvement | patch |

### 2.3 How to write release notes (keep it under 20 lines)

```markdown
## v1.2.0

One sentence: the most important change in this release.

### Upgrade notes
- Breaking changes and migration steps; if none, say "no breaking changes".

### Added / Changed / Fixed
- No more than five bullets each; link to the CHANGELOG or PRs for detail.

### Known issues
- …

### Verification
- artefact hashes / signatures (only when you ship binaries)
```

**The test**: can a user decide, **from the release notes alone**, whether to upgrade now and what they must change?

### 2.4 When a release *process* document is worth writing

Only when the process is complex enough to require handover (multi-platform builds, signing, package repositories).
`cli/cli`'s `release-process-deep-dive.md` is the model, and it opens by stating why: *the maintainers who built the
workflow had all left, and the current ones kept re-investigating it*. Simple projects don't need a runbook — the
release steps belong in the `AGENTS.md` command table.

## 3. Running: state and to-dos

### 3.1 Admit it: there is no pure-documentation solution

Tool-side mechanisms cover only part of the problem:

| Mechanism | Covers | Does not cover |
|---|---|---|
| session resume (`--continue` / `--resume`) | the same session on the same machine | a new session, another machine, another person |
| auto memory (`MEMORY.md` + topic files) | sessions on the same machine | not in git; lost on another machine |
| subagent memory (`memory: project`) | committable, cross-machine | serves only that subagent |

And "write it into the repo" does not happen by itself either. This repository was its own counter-example:
PRs #3–#6 each had a **163-character** body of boilerplate, there were **zero** open issues, and commits carried only a
title. A new session could answer "**what was done**" but not "**what's next**".

**Conclusion: state must live somewhere that exists by necessity; documentation maintained from memory will be forgotten.**

### 3.2 Three carriers, ranked by reliability

| Approach | Reliability | Use when | Cost |
|---|---|---|---|
| **A. Write it down from memory** | low | not recommended | it is forgotten, goes stale, and becomes a second source of truth |
| **B. Required template fields + review** | medium | a repo with reviewers | a missing field is caught in review; nothing catches it otherwise |
| **C. Build it into the tooling** | high | **there is already an automated release path** | one or two extra required arguments; unusable offline or without a token |

Approach C means: make "next step / non-goals / how it was verified" **required arguments of the release process**.
The consequence of omitting them is **you cannot publish**, rather than documentation quietly going stale —
**this is the only enforcement point that does not depend on memory.**

### 3.3 Recommended rules

1. **Automated release exists** → use **C**: require "next step (write `none` explicitly if there is none)" and
   "non-goals", and structure them into the PR description.
2. **Manual PRs, but there are reviewers** → fall back to **B**: those fields are required in the PR template.
3. **Solo, no reviewers** → a simplified B: keep the fields, and put "**last updated + the PR number it is based on**"
   on the status line. It still goes stale, but **the staleness is visible**.
4. **Never create a separate state file** (`PROGRESS.md` / `STATUS.md` / a `sessions/` directory): it becomes a second
   source of truth next to PRs and issues.

### 3.4 Three things not to do

- ❌ **No `PROGRESS.md` / `STATUS.md` / `sessions/`**: multiple sources of truth, and one file per session turns into noise.
- ❌ **Don't have a checker judge "is the state fresh"**: `mtime` is reset by `git clone`, so such a rule passes on every
  CI run and every new machine — it measures *when you cloned*, not *whether the state is current*.
- ❌ **Don't put a to-do list in `AGENTS.md`**: it eats the per-session context, and lists are the most perishable thing there is.

### 3.5 Handover criteria

A new session reads **three things** and answers **four questions**:

| Read | Answer |
|---|---|
| the most recent PR title and description | where we are |
| open issues / PRs | what's next |
| `AGENTS.md` | what must not be touched, and why it is this way (ADRs if needed) |

Plus one discipline: **run a command to reconcile before acting.** What a file claims may be stale; what executes is true.

## 4. The state of this repository (honest record)

- **Planning**: no `docs/spec/` — this is a continuously evolving spec, not a one-off project with a scope baseline.
- **Running: approach B plus a platform constraint** (since 2026-11-17). It used to be approach C (a script made
  `-Next` mandatory), but this library removed every executable ([ADR-0009](../docs/adr/0009-spec-only-no-tooling.md)).
  What holds now is the **four-section PR template** plus the **single human approval** the ruleset requires.
  The cost is honest: **template fields can be skipped**, so this now rests on review rather than on a mechanism.
  [ADR-0005](../docs/adr/0005-publish-requires-next-step.md) records the original decision; its mechanism was retired with ADR-0009.
