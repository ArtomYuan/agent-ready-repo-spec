# 07 · Which settings to turn on

**English** · [简体中文](07-该开哪些设置.zh-CN.md)

> This chapter is a **checklist of switches**, not a set of decisions. The decisions ("which tier, who may bypass")
> live in [guide/00](00-接入决策.md); this chapter is where you actually click.
>
> Basis: GitHub's own documentation for rulesets and repository settings, plus one incident that cost this repository a
> blocked main branch ([ADR-0010](../docs/adr/0010-required-checks-self-lock.md)).

---

## 0. One principle

**A setting is a constraint that does not depend on memory.** If something must always hold, express it as a platform
mechanism — not as a sentence in a document.

The corollary matters just as much: **every switch you turn on must have an owner.** A settings page nobody is
responsible for is one nobody will fix when it locks the repository.

---

## 1. Merging — turn all of these on

| Setting | Value | If you don't | Where |
|---|---|---|---|
| Require a pull request | on | direct pushes bypass every gate you built | Settings → General → Pull Requests |
| Merge method | **squash only** | history mixes merge commits with squashes; revert becomes guesswork | same page |
| **Automatically delete head branches** | on | merged branches pile up (this repository had 13 at one point) | same page |
| Allow auto-merge | on (optional) | every merge needs a human click even after approval | same page |

> **Note on auto-delete**: it only fires on **merge**. A branch whose PR was *closed* stays forever — delete those by hand.

---

## 2. Rulesets / branch protection — turn all of these on

| Rule | Value | If you don't |
|---|---|---|
| `deletion` | on | the default branch can be deleted by accident |
| `non_fast_forward` | on | force push destroys history; any revert plan dies with it |
| `required_status_checks` | the checks that actually exist | see §6 — a wrong name blocks main permanently |
| `pull_request` → approvals | **≥ 1** | an agent can merge its own work unreviewed |
| `pull_request` → dismiss stale reviews | on | an approval given before the last commit counts as if nothing changed |
| `pull_request` → **require approval of the last push** | on | whoever pushed last can approve themselves |
| `pull_request` → require Code Owners review | on **if** you have `CODEOWNERS` | the file becomes decoration |
| `pull_request` → required review thread resolution | on | unresolved "we should change this" comments get merged anyway |
| `required_linear_history` | on | history becomes unreadable; cherry-pick and audit get harder |

**Allowed merge methods**: squash only. Mixing methods is how a repository ends up with three shapes of history.

---

## 3. Who can bypass — decide it explicitly

| Question | Recommended answer |
|---|---|
| Can admins bypass? | **No.** If you need an escape hatch, name it explicitly (ruleset bypass list), not by leaving admin bypass on |
| Who may edit the ruleset? | write the person or team into the adoption record |
| What happens when it locks? | a one-paragraph break-glass procedure, also in the adoption record |

Why this is `must`: **the person writing the code and the person who can change the gate are often not the same person.**
A token that can push usually cannot edit rulesets — we hit exactly this
([ADR-0010](../docs/adr/0010-required-checks-self-lock.md)).

---

## 4. Actions — tighten the defaults

| Setting | Value | If you don't |
|---|---|---|
| Workflow permissions (default `GITHUB_TOKEN`) | **read-only** | every workflow silently has write access to the repository |
| Allow GitHub Actions to create and approve pull requests | off | a workflow can approve its own PRs |
| Fork pull request workflows | **require approval for first-time contributors** | a stranger's fork can run code in your runners |
| Allowed actions | "Allow select actions" (or at minimum: no unpinned third-party) | supply-chain risk with no review path |
| Log / artifact retention | shorten it (e.g. 30 days) | storage grows forever and nobody notices |

---

## 5. Security — on by default, cheap to keep

| Setting | Value | If you don't |
|---|---|---|
| Private vulnerability reporting | on | researchers have no private channel; reports land in public issues |
| Dependabot alerts | on | you learn about a vulnerable dependency from a stranger |
| Dependabot security updates | on | alerts without updates are just noise |
| Secret scanning (+ push protection) | on where available | a leaked token is only discovered after it is used |
| Code scanning | optional | worth it when you ship code, noise when you only ship markdown |

## 6. The one setting that will lock you out

`required_status_checks` stores **names**, and each name needs something to report it. Delete the workflow or rename the
job and that name stays `Expected — Waiting for status to be reported` **forever** — no timeout, and historical runs
don't count.

Rules:

1. Pick check names from the **dropdown**, never type them (a single wrong character in a non-ASCII name is invisible
   in the UI and fatal in effect).
2. Rename a job in three steps: add the new-named job → repoint the ruleset → delete the old job in a later PR.
3. Write the current required-check names into `AGENTS.md` so the next person knows what the workflow is holding up.

Full incident: [guide/05 appendix](05-Agent参与怎么管理.md) · [ADR-0010](../docs/adr/0010-required-checks-self-lock.md).

## 7. Record the settings, not just the clicks

Put a `## Settings` section in your adoption record ([templates/adoption.md.tmpl](../templates/adoption.md.tmpl)):

```markdown
## Settings（2026-11-18）

| 设置 | 值 | 谁能改 |
|---|---|---|
| 合并方式 | 只允许 squash | @owner |
| 必需检查 | 链接检查、双语配对 | @owner |
| 管理员绕过 | 不允许；破窗见 ADR-0010 | @owner |
| Actions 默认权限 | 只读 | @owner |
```

Without "who can change it", the table records a wish, not a state.

## 8. What this repository actually has

| Setting | State |
|---|---|
| Require a pull request | on |
| Squash only | on |
| Automatically delete head branches | on (turned on 2026-11-17, after 13 stale branches accumulated) |
| Ruleset `main` | `deletion` · `non_fast_forward` · `required_status_checks`（链接检查 / 双语配对）· `pull_request`（1 approval, dismiss stale, require last push approval, thread resolution）· `required_linear_history` |
| Admin bypass | none (`bypass_actors: []`) — which is why the App token cannot edit the ruleset |
| Actions default permissions | **not yet verified** — a real gap, listed here rather than hidden |
