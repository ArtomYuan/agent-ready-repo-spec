# 规范正文

这一节说明**怎么读这套规范**。规则索引见 **[rules/README.md](rules/README.md)**（一行一条，含旧号、档位、级别、路径）；
**判据正文在各规则文件里**，索引不复制它。

## 一个仓库的四个成熟阶段

级别只回答一件事：**这一档在解决什么问题**。要哪些文件、每条怎么判，一律看
**[rules/README.md](rules/README.md)**——本节不重复它（重复就会漂移）。

| 级别 | 这一档在解决什么问题 | 一句话判据 |
|---|---|---|
| **L0** | 接手成本 | 人和 agent 都能在 30 秒内接手 |
| **L1** | 协作入口 | 外部贡献者不会问"我该怎么提" |
| **L2** | 可追溯 | 有事能查、有决策能追溯 |
| **L3** | agent 参与的可持续性 | agent 的改动可拒绝、可回滚、不腐烂 |

**级别是累积的**：L2 隐含 L0+L1。判断"我到了哪一级"，用**你自己选的目标级别**去比对，
不要拿别人的档位要求自己（见 [guide/00](../guide/00-接入决策.zh-CN.md)）。

> **表里没有文件清单，是刻意的。** 旧版本在这里列过"达到它意味着有 README / CONTRIBUTING / …"，
> 而那份清单和 checklist 的严重度**互相矛盾**：它把 `R005`（CI，`should`）、`R010`（CONTRIBUTING，`may`，
> 且正文明说"不是 agent 就绪的必要条件"）写成了达标条件，又在 L3 写了"可回滚"——而清单里根本没有回滚条目。
> 现在这一节只描述问题，判据只有一份。

## 三档严重度

| 严重度 | 含义 | 典型 |
|---|---|---|
| `must` | 缺了就是硬伤，会在几周内咬人 | 提交了 `settings.local.json`、`.gitignore` 没排除个人配置 |
| `should` | 该有；没有会让协作或治理变形 | 无 CODEOWNERS、无 ADR、`permissions.deny` 为空 |
| `may` | 加分项，视项目规模取舍 | 无 CODE_OF_CONDUCT、无 `.editorconfig`、无 `.gitattributes` |

`may` **不阻断**你达到某个级别。这是刻意的：小项目不该被"加分项"判红。

## 符合性声明

规范要能被"符合"，否则它只是建议。一个仓库可以在自己的文档里写：

> 本仓库符合 `agent-ready-repo-spec 2.0.0`，目标档位 **L2**。

**声明的四个条件**——缺任何一条就不该这么写：

| # | 条件 | 谁来查 |
|---|---|---|
| 1 | L0…目标档位的**全部 `must` 条目**都满足 | 结构性判据，可逐条核对 |
| 2 | 每一个**未满足的 `should`** 都有书面理由 | 理由落在采用记录里，不落在聊天记录里 |
| 3 | 采用记录存在于**被管理的那个仓库内**，含 `specVersion`、目标档位、决策人、复审日期 | [templates/adoption.md.tmpl](../templates/adoption.md.tmpl) |
| 4 | `may` 条目**不影响**符合性——没做到 `may` 不是不合格 | 刻意如此 |

**关键词口径**（对应 RFC 2119）：

| 清单里的级别 | 含义 | 不满足时 |
|---|---|---|
| `must` | 必须（MUST） | **不能声明该档位** |
| `should` | 应当（SHOULD） | 可以声明，但必须写出偏离理由 |
| `may` | 可以（MAY） | 与符合性无关 |

**谁来评：仓库自己声明，别人只报事实。**
[agent-playbook.md](agent-playbook.md) §2 的"不要给分数，不要给等级"约束的是**替人干活的 agent**——
它只输出"已有 / 建议补 / 跳过 + 理由"。档位由仓库主人自己选、自己声明、自己复审。
这两句不冲突：一句说"你别替我评"，一句说"你要对自己的声明负责"。

**声明什么时候作废**：`specVersion` 一升，声明就自动转为待复核——
按采用记录里的复审日期重新过一遍 [rules/README.md](rules/README.md)。
判据收紧是 **major**（见下节），正是为了让"上次合格"不会悄悄变成"现在不合格"。

## 判定靠什么

清单里的每一条都是**结构性判据**：文件在不在、字段有没有、行数超没超、引用还存不存在。

- **没有**"代码质量""测试覆盖率"这类需要主观判断的条目——那种规则会立刻被绕过。
- **没有**"必须用某家 CI / 某个模型 / 哪个 agent 工具"——规范只管可验证的痕迹，不管工具选型。
- 需要判断力的部分，靠**读者**按 [guide/03](../guide/03-文档该怎么写.zh-CN.md) 的判据去读，而不是靠清单。

> 想让机器判？可以，但那是**另一个项目**：本库只提供文本，谁想自动化就自己解析 `rules/README.md`
> 或另建数据。理由见 [ADR-0009](../docs/adr/0009-spec-only-no-tooling.md)。

## 提交规则（5 条，分三层）

| 规则 | 级别 | 查什么 | 为什么在这一层 |
|---|---|---|---|
| `R028` | L2 · **may** | 有 `commitlint` 这类**执行载体** | 不是业界基线（`actions/checkout` 只给一条外链），要自动生成 CHANGELOG 时才值得 |
| `R041` | L3 · **may** | 仓库自己的提交约定写进 `AGENTS.md` | agent 默认自带提交/PR 指令，仓库另有约定不写明就会两套打架 |
| `R029` | L2 · should | agent 提交归属未被关闭（`attribution`） | 默认会写 `Co-Authored-By` trailer，关掉就失去审计线索 |
| `R050` | L3 · may | 最近提交的 subject 符合 Conventional Commits | 历史是唯一无法事后伪造的证据 |
| `R051` | L3 · may | 最近提交是线性历史 | 线性历史让 revert / cherry-pick / 审计都简单 |

`R050`/`R051` 需要看 `git log`，属于**抽样自查**，不是每位使用者都必须做的事。
原则：**能查就查，查不到就说"跳过"，绝不说"通过"。**

## 一条与语言有关的条目（`writing/agents-md-language`，旧 `R042`，L3 · may）

它和提交规则无关，单独说明，因为它最容易被误解成"规范要管你用什么语言"：

- **它管的是"有没有声明"，不是"声明成什么语言"。** 声明中文、英文、日文都行。
- 只到 `may`：没有真实事故支撑——有仓库写了沟通偏好（`kubernetes/kubernetes`），但没有证据表明缺了它就会出事。
- 为什么还要有：agent 的语言默认跟着代码注释或它上次的输出来走；不声明，同一仓库会出现两种语言，而 review 每次都要纠正。

## 版本策略

- `specVersion` 遵循 SemVer（当前 **2.0.0**）。
- **新增 `may`/`should` 条目** → minor。
- **把条目改成 `must`，或收紧判据** → major（照做的人会突然"不合格"）。
- **改规则 ID、改板块划分、改规则文件路径 → major。** 判据一个字没动，
  但所有指向旧 ID / 旧路径的引用当场失效——对下游这是破坏性变更，和收紧判据同级。
  2.0.0 就是按这一条定的。
- **改判据措辞但不改判定结果** → patch（错别字、补一个例子、把话说清楚）。
- **升了哪一位、为什么，要写出来** —— 见 `release/version-bump-why`（旧 `R070`）。
  没有这句话，上面几条策略就没人能被判定违反。
- 旧条目**只废弃不删除**（文件保留、索引行标 `deprecated`），保证历史讨论还能对齐。
- **旧号永不复用、永不改**；规范名是 `板块/主题`（见下节「编号」）。

## 编号

规则的**规范名是 `板块/主题`**，例如 `release/moving-tags`。它同时就是文件路径
（`spec/rules/release/moving-tags.md`），所以**名字和路径不可能各说一套**。

1.x 时代的 `R0xx` 降级为**旧号**，永久保留在 [rules/README.md](rules/README.md) 的「旧号」列：

| 标识 | 谁在用 | 能不能改 |
|---|---|---|
| `release/moving-tags` | 新写的文档、新的采用记录 | 可以改，但改路径 = 破坏性变更 → **major** |
| `R067` | 历史 PR、CHANGELOG、ADR、已发出去的采用记录 | **永不可改、永不复用** |

### 命名规矩

- 全小写 kebab-case；板块名一个词，主题名 1–3 个词。
- **一条规则一个文件**，文件名就是主题名。
- **板块名一经发布不再改**——它编码在每条 ID 里，改板块名等于批量改 ID。
  2.0.0 定下的 8 个板块：`adoption` `documents` `layout` `writing` `agent-config` `governance` `release` `settings`。
- 新增条目 = 新建一个文件 + 在 [rules/README.md](rules/README.md) 对应档位节加一行。**不插号、不回收旧号。**
- 废弃条目 = 文件保留，索引行标 `deprecated`。当前没有废弃条目。

### 历史号段（读旧 PR 时有用，别拿它推断级别）

`R001`–`R009`=L0、`R010`–`R019`=L1、`R020`–`R029`=L2、`R030`–`R049`=L3、`R050`–`R059`、`R060`+ 续段。
那只是 1.4.0 之前的**历史巧合**，不是约定：1.5.0 要加 L2 条目时发现 `R020`–`R029` 已用满，只能往后开。
`R006`–`R009`、`R017`–`R019` 从未被分配（已用 `git log --all -S` 核对全部历史提交）。
**2.0.0 起号段不再增长**，档位以索引的分节为准。

## 规范不覆盖什么

以下内容有意排除，因为无法稳定判定，且容易变成走过场：

- 提交信息**内容**写得好不好（只管格式与载体）
- 测试覆盖率阈值
- 代码风格
- "文档写得好不好"（给判据，不给分数）
- 替你评"你该到哪一级"——档位由仓库自己选、自己声明，别人只报事实（见上文「符合性声明」）
- 用了哪个 CI / 哪个模型 / 哪个 agent 工具
