# Agent 操作手册：怎么用这套规范管一个仓库

> 给 agent 读的。人的版本是 [../README.md](../README.md)。
> 读完之后你的任务不是“让分数变高”，而是**让这个仓库在半年后还能被接手**。

---

## 0. 先建立心智模型：四层，别混

| 层 | 载体 | 谁写 | 作用 |
|---|---|---|---|
| 意图 | `README` / `docs/` | 人 | 这个仓库为什么存在 |
| 事实 | `AGENTS.md` | 人，agent 可提议 | 每次会话都要知道的命令与约定 |
| 执行 | `.claude/`（权限、hooks、skills） | 人 | 把“建议”变成“强制” |
| 记录 | `CHANGELOG` / `docs/adr/` / PR / commit | 人和 agent | 半年后回答“为什么是这样” |

**最常见的错误是在错误的层解决问题**：把硬约束写进文档（执行层缺失）、把每次都要用的命令写进 skill（事实层缺失）、
把决策只留在 PR 讨论里（记录层缺失）。

一条判断法则：**同一条规矩，第二次被违反就换一层。**

---

## 1. 主循环：体检 → 分诊 → 修 → 复验

```bash
# 1) 体检
pwsh ./checker/spec-check.ps1 -Target <path> -Level 3 -Format json

# 2) 修一个级别（不要跨级）

# 3) 复验：看 achievedLevel 有没有前进
pwsh ./checker/spec-check.ps1 -Target <path> -Level 3 -Format json
```

**不要跳过 1 直接建文件。** 存量仓库里往往已经有比模板更好的东西，盲建就是破坏。

---

## 2. 分诊：不同 FAIL，处理方式完全不同

拿到 JSON 后按这个表处理，**不要按规则 ID 顺序处理**。

| FAIL 的形态 | 典型规则 | 你的动作 |
|---|---|---|
| **硬伤**（`must`） | R025 提交了 `settings.local.json`、R036 没排除个人配置 | 立刻修，不要排在后面 |
| **缺文件、有标准答案** | R010 `CONTRIBUTING`、R020 `SECURITY`、R012 PR 模板 | 用 `templates/` 建，填真实值 |
| **缺文件、需要人决定** | R004 协议类型、R011 owner 是谁、R020 SLA 数字 | **停下来问**，不要猜 |
| **有文件但不合格** | R030 `AGENTS.md` 太长、R033 `CLAUDE.md` 不是薄层、R013 模板缺 frontmatter | 合并式修改，保留原有内容 |
| **引用失效** | R037 `AGENTS.md` 里的死链 | 修正路径或删除句子；**不要**为了过检删掉整节 |
| **结构性缺失** | R023 无 ADR、R022 无文档地图 | 先写一条最真实的 ADR（刚做过的那个决定），不是编一条 |

三条铁律：

1. **先硬伤，后缺件，最后加分项。**
2. **一次只推进一个级别。** L0 全绿再动 L1。
3. **不许用“删规则 / 降 severity / 加豁免”过检。** 规则是产品本身。

---

## 3. 从 L0 往上，每一步具体做什么

### L0：能读、能跑

- `README.md`：一句话定位 + 30 秒能跑起来的命令 + 入口链接。不写架构。
- `AGENTS.md`：**先写短的**。命令 + 目录地图 + 3 条硬约定 + 3 条禁区 + 已知的坑。
- `.gitignore`：先放 `.claude/settings.local.json`、`CLAUDE.local.md`、`.env*`。
- `LICENSE`：没有就选 MIT（内部库也要有，避免“默认保留全部权利”）。
- CI：一个 `ci.yml`，跑 lint + test。**没有 CI，后面所有门禁都无处挂载。**

### L1：能被别人贡献

- `CONTRIBUTING.md`：分支命名、提交格式、PR 流程、**评审 SLA 数字**（写“尽快”等于没写）。
- `CODEOWNERS`：按路径指派到**人类团队**。必须同时开 “Require review from Code Owners”，否则这个文件不生效。
- PR 模板：改动 / 理由 / 影响面 / **怎么验证的（贴输出）** / 自检清单。
- Issue 模板：`.yml` 必须有 `name` + `description`，否则社区档案不打勾。
- `CHANGELOG.md`：从 `## [Unreleased]` 起，只写用户可感知的行为变化。

### L2：能对外、能追溯

- `SECURITY.md`：支持版本 + 私密上报入口 + 响应时限。**引导走公开 issue 等于没有安全策略。**
- `docs/index.md`：文档地图。没有地图，人和 agent 都靠猜。
- `docs/adr/0001-*.md`：写**已经发生过的**那个真实决定，不是编一个。
- `.claude/settings.json`：只放声明式 `permissions.deny`（`Read` 密钥、`Edit` 受保护路径、`Bash` 破坏性命令）。

### L3：agent 主参与的治理

- `AGENTS.md` 压到 200 行内：模块级规则移到 `.claude/rules/`（带 `paths`），多步流程移到 skill。
- `CLAUDE.md` 只留 `@AGENTS.md` + 少量专属（≤40 行）。**双事实源比没有事实源更糟。**
- hook 引用的脚本必须存在——指向不存在的脚本等于门禁静默失效。
- `.claude/skills/*/SKILL.md` 必须有 `name` + `description`；`description` 决定它会不会被自动命中。
- 文档引用必须有效（R037）：重构后失效的路径是“agent 照错路干活”的头号原因。

## 4. 什么时候必须停下来问人

满足任一条，**停**：

- 需要决定**协议、团队名、SLA 天数、支持版本**这类组织信息。
- 要**改规则本身**（`rules/rules.json`）。
- 要**改 `.claude/` 或 `.github/workflows/`**——这是治理面，必须走人工 PR。
- 目标仓库是**第三方/公开仓库**：只做只读体检，不提交任何改动。
- 修一条 FAIL 需要**删除已有内容**（不是补充）。
- 你发现**两条规则互相矛盾**——这是规范 bug，报上去，别自己挑一条遵守。

## 5. 反模式（agent 侧）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 为了让分数好看，批量生成空模板 | 占位内容本身是负债，下次体检还是红 | 只建**立刻能用**的文件，其余留 issue |
| 把 `AGENTS.md` 写成百科 | 每次会话烧 context，遵守率下降 | 超 200 行就拆 `rules/` 和 skill |
| 在 `CLAUDE.md` 里复制一份 AGENTS.md | 双事实源，随机生效 | `@AGENTS.md` 导入 |
| 用 hook 脚本做 `Edit(./prod/**)` 能做的事 | 维护成本、跨平台重写 | 先用 `permissions.deny` |
| 报告里只写“共 12 个问题” | 人无法排优先级，等于没报告 | 三段式：达成等级 / 硬伤 / 阻断项 + 顺序 |
| 修完不重跑 | 不知道有没有真的前进 | 每次修复后复验 `achievedLevel` |

---

## 6. 一句话

**体检报告不是 KPI。**它的用途是：告诉你下一步该动哪一层，以及哪一层已经在腐烂。
