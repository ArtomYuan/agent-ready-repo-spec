# 发布物规则

> 板块 `release` · 本页承载 4 条条目：`release/tag-and-release`（L2 · should · 旧 `R064`）·
> `release/changelog`（L1 · should · 旧 `R014`）· `release/moving-tags`（L2 · should · 旧 `R067`）·
> `release/superseded-tags`（L3 · may · 旧 `R068`）
> 讲解与出处见 [guide/06 §2 开头与 §2.5](../../../guide/06-信息该放哪.zh-CN.md)。

一次发布产出**三样东西，别混**。它们可变性不同，所以规则完全不同：

| 产物 | 内容 | 面向谁 | 会不会变 |
|---|---|---|---|
| **tag** | 不可变指针（`v1.2.0`） | 工具链、CI、下游 lock | **永不改** |
| **GitHub Release** | 本次公告："你能感知到什么" | 使用者 | 发完基本不改（勘误可补） |
| **CHANGELOG** | 累积记录，按版本分组 | 使用者 + agent | 随版本不断追加 |

这一篇管这四件事：三样产物怎么对齐、tag 打在哪、tag 能不能移动、废弃 tag 怎么处理。
正文写什么见 [内容规则](content.md)，版本号怎么定见 [版本号规则](version.md)。

## 一次发布的标准动作

顺序不能换，因为**后一步的落点由前一步决定**：

1. 一个提交，把 CHANGELOG 的 `[Unreleased]` 转成版本节（并按 `release/version-bump-why` 写明升了哪一位）；
2. 在**该提交**上打 tag；
3. 建 Release 页，正文按 [内容规则](content.md) 的四节写。

第 2 步的"**该提交**"是这条规则的全部难点：tag 必须指向一棵**包含本次版本节**的树。
打在转换之前的提交上，钉住这个 tag 的人拿到的 CHANGELOG 里没有这个版本。

## tag 打错了怎么办

先承认：上面说 tag 永不改，那是规矩，现实偶尔会破例。所以把程序写清楚——因为
**移动 tag 是破坏性变更，哪怕树里一个字节都没变**。

按这个顺序判：

1. **优先发一个更正版本，而不是移动 tag。** `v1.4.0` 指错了提交？就在对的提交上发 `1.4.1`，
   `v1.4.0` 原地不动。钉住 `v1.4.0` 的人保住一个可复现的世界，跟着版本范围走的人拿到更正。
2. **只有旧 tag 根本不可用时才移动**——它指向一棵构建不出来的树，或指向一个从未真正发过的版本。
   此时把**旧 SHA、新 SHA、原因**同时写进 Release 正文与 CHANGELOG，把被取代的 tag 页标好
   （见下），能看见谁钉过就去通知谁。
3. **绝不静默移动 tag。** 移动一个 tag 就是对所有钉住它的人毁约，而且这次损坏是隐形的：
   他们的构建变了，手上却没有 diff 可读。

第 1 步和第 2 步之间有个容易踩的判断坑：**"更正版本"必须内容更多，不能更少。**
如果错锚的 tag 指向的树其实是**超集**（它包含了后来的提交），那在它上面发一个更高版本号、
更少内容的版本，是**倒退**——这种情况下第 1 步不适用，直接走"记录偏差"。
本库 `v1.4.0` 就是这个情形，见 [ADR-0012](../../../docs/adr/0012-release-notes-spec.md) 与本库 `2.0.0` 的已知问题。

## 废弃的 tag 不删

删 tag 会让已经引用它的构建**彻底复现不出来**。标废既保住复现，又挡住新使用者：
在该 tag 的 Release 页写明"请勿使用，改用 `vX.Y.Z`"。本库 `v1`（指向含 `checker/` 的旧树）
就是这么处理的。

## 条目

### 存在 CHANGELOG

`release/changelog` · L1 · should · 旧 `R014`

**为什么。** CHANGELOG 是 agent 判断"这个 API 还能不能用"的第一手依据，也是行为契约。

**怎么做。** 按 Keep a Changelog 建 `CHANGELOG.md`，只写用户可感知的行为变化。

### 每个发布版本都有 tag 和 Release 页，tag 锚在发布提交上

`release/tag-and-release` · L2 · should · 旧 `R064`

**为什么。** `SECURITY.md` 承诺"只对最新 `specVersion` 提供修复"——没有一个可锚定的 tag，
这句就是空话，下游也无从固定引用。本库曾只有 `v1`，指向含 `checker/` 的旧树。

**怎么做。** 发版 = 一个把 `[Unreleased]` 转成版本节的提交 → 在**该提交**上打 tag → 建 Release。
三件产物的分工见 [guide/06](../../../guide/06-信息该放哪.zh-CN.md) §2。

### 移动 tag 要留痕（旧 SHA / 新 SHA / 原因），且优先发更正版本

`release/moving-tags` · L2 · should · 旧 `R067`

**为什么。** tag 可以被移动，而钉住它的人会**静默**拿到另一棵树——这是没有 diff 可读的
破坏性变更，比改代码更隐蔽。

**怎么做。** 能发 `1.4.1` 就别动 `1.4.0`；确实要动，就把三个值同时写进 Release 正文与 CHANGELOG。
程序见 [guide/06](../../../guide/06-信息该放哪.zh-CN.md) §2.5。

### 废弃 tag 标 *Superseded* 并指向替代 tag，不删 tag

`release/superseded-tags` · L3 · may · 旧 `R068`

**为什么。** 删 tag 会让已经引用它的构建彻底复现不出来；标废既保住复现，又挡住新使用者。

**怎么做。** 在该 tag 的 Release 页写明"请勿使用，改用 `vX.Y.Z`"。本库 `v1` 就是这么处理的。
