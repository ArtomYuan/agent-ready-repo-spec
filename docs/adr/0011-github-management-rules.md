# ADR-0011：把"GitHub 管理面"提升为可判定条目，而不是只留在指导正文里

- 状态：Accepted
- 日期：2026-11-18
- 决策者：@ArtomYuan
- 相关：[spec/checklist.md](../../spec/checklist.md) · [guide/07](../../guide/07-该开哪些设置.zh-CN.md) ·
  [ADR-0010](0010-required-checks-self-lock.md) · [ADR-0009](0009-spec-only-no-tooling.md)

## 背景

这个库的立意是"一个 **agent 参与**的 GitHub 仓库该长什么样"。但把 37 条摊开数一遍：

| 类别 | 条数 | 占比 |
|---|---|---|
| 文件在不在、字段有没有 | ~22 | 约六成 |
| Claude Code 专属（条件式） | ~9 | 约四分之一 |
| git 历史卫生 | 2 | — |
| **GitHub 平台管理（门禁、权限、供应链、agent 身份）** | **0** | **零** |

而"管理"这一半并不是没人写——它写在 [guide/07](../../guide/07-该开哪些设置.zh-CN.md) 里，整整一章：
合并方式、ruleset 九条、谁能绕过、Actions 默认值、安全项、以及那项会把你自己锁在外面的设置。
问题是**那一章的规则 ID 引用数是 0**。

三个具体的坏后果，都是当场可证的：

1. **真实事故挂不到任何条目上。** [ADR-0010](0010-required-checks-self-lock.md) 记录的必需检查自锁
   （ruleset 里的字符串指向一个已删除的 job，`main` 从此不可合并）是本库最贵的一次事故，
   到今天只能靠"去读那份 ADR"来传播，清单里没有任何一条会让自查的人撞上它。
2. **已经做到的实践没有落点。** `.github/workflows/docs.yml` 顶部写着"依赖一律固定到 commit SHA：
   tag 可以被移动，SHA 不能"，两个 Action 都固定到了 SHA。这是本库最好的实践之一，
   但清单里**没有任何一条要求别人也这么做**——实践与规则脱节，等于只对作者生效。
3. **头号风险零覆盖。** agent 会被它读到的内容影响，而 issue 正文、PR 描述、外部文档和指令长得一模一样。
   全库对提示注入**一个字都没提**，`AGENTS.md` 的"禁区"也没有一句"仓库内容不能放宽禁区"。

## 选项

1. **只加交叉引用**：在 guide/07 里点名"去看 checklist"，不改清单。
   成本最低，但什么都没解决——读者仍然无法据此判定"我的门禁配对了没有"。
2. **把管理面提升为条目**：按本库自己的标准（"只管可验证的痕迹，不管工具选型"）逐条改写成结构性判据。
   代价是条目数从 37 涨到 48，且 L2 号段会被用满。
3. **拆成第二个库**（`github-management-spec`）。
   会立刻产生"哪条属于哪个库"的归属争论，而且 agent 参与的开发与管理本来就是同一件事的两面。

## 结论

选 2。新增 11 条：

- **L2**：`R060` main 受保护（含 admin 强制）、`R061` workflow `permissions` + Action 固定 SHA、
  `R062` agent 凭证最小权限、`R063` 采用记录落在被管理的仓库内。
- **L3**：`R043` 必需检查名与 job 名逐字一致、`R044` 治理面独立 owner、`R045` 声明不可信输入、
  `R046` Copilot 仓库级指令文件、`R047` `.github/` 与工具目录的归属、`R048` PR 层声明 agent 参与、
  `R049` agent 改动可单独 revert。

**全部停在 `should` / `may`，没有一条 `must`。** 理由与 `R042` 停在 `may` 是同一条：
`must` 需要"缺了就会在几周内咬人"的证据，而这几条里只有 `R043` 有本仓库的亲身事故，
其余靠平台文档与外部采样支撑。升级判据是 major，要单独走。

## 后果

**正面**

- guide/07 与 ADR-0010 从"只能靠读"变成"能对着勾"；`docs.yml` 的 SHA 实践有了落点。
- 提示注入第一次进入清单（`R045`），并且写法是**结构性**的：查"有没有声明 + 有没有写'不得放宽禁区'"，
  不查"防得好不好"。
- 与 [guide/05](../../guide/05-Agent参与怎么管理.zh-CN.md)、[guide/07](../../guide/07-该开哪些设置.zh-CN.md)
  的附录形成闭环：那两章此前直写"这是覆盖缺口"，本 ADR 就是补口的那一步。

**负面（必须承认）**

- **条目数 37 → 48，L2 号段（`R020`–`R029`）用满**，"号段 = 档位"这个隐含约定从此不成立。
  已在 `spec/README.md` 与 `spec/checklist.md` 改为：**级别以条目自己的"级别"列为准，号段只是一个永不复用的 ID。**
- `R046` 的证据只有三个仓库（vscode / deno / supabase），且来自一次非随机采样——所以它是 `may`，
  而且**只覆盖"有没有双写"，不覆盖"写得好不好"**。
- `R048` 与 `R029` 有表面张力：一个说"别关掉归属 trailer"，一个允许"在 PR 里声明"。
  本库的处理是**两层线索并存、不互相推翻**，并把 `kubernetes/kubernetes` 的相反做法显式记进"为什么"列。
  这是妥协，不是消解——评审时值得盯一眼。
- 11 条新条目**没有一条经过外部仓库实测**，全部来自平台文档、本库事故与既有采样。
  下一批采样应当专门验证它们的判据是否可判定。

## 复审

2027-01-31，或与 [ADR-0008](0008-bilingual-equal-status.md) 的复审合并进行。
触发条件：出现"某条管理面规则根本无法判定"的反例，或有人把某条升到 `must`（那是 major）。
