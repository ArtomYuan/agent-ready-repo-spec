# ADR-0013：规则改成一条一个文件，ID 换成 `板块/主题`

- 状态：Accepted
- 日期：2026-11-20
- 决策者：@ArtomYuan（提出结构）、agent（方案与执行）
- 取代：**部分修订** [ADR-0009](0009-spec-only-no-tooling.md) 的落点约定
  （"唯一事实源 = `spec/checklist.md` 一个文件"→"一条规则一个归属文件 + 一份索引"）
  —— ADR-0009 的**理由不变**，见下面「为什么不违反 ADR-0009」
- 相关：[spec/rules/README.md](../../spec/rules/README.md) ·
  [spec/README.md](../../spec/README.md)「编号」「版本策略」 ·

## 背景

`spec/checklist.md` 到 1.6.0 已经装了 **55 条**规则，一张表从头滚到尾。三个问题同时到期：

1. **`R0xx` 没有辨识度。** reviewer 问"版本号那里不需要加后面的解释吧？"，
   要回答这个问题得先查 `R070` 是什么。在 PR、issue、采用记录里写 `R067`，
   读者必须跳一次表才知道在说什么——**编号越稳定，越难读**。

2. **判据和它的解释分居两个文件，这是本库反复出血的伤口。**
   [ADR-0011](0011-github-management-rules.md) 修的是"有章节没条目"（07 章论证了半天，清单 0 条）；
   [ADR-0012](0012-release-notes-spec.md) 修的是同一处（06 章 §2 写完了发布规矩，清单 0 条）；
   `release/version-bump-why`（旧 `R070`）是第三例（SemVer 策略写在 `spec/README.md`，清单 0 条）。
   **三次都是同一个结构原因**：判据在 `spec/`，解释在 `guide/`，中间靠一张手写的章节索引连着，
   而这张索引没人核对。

3. **档位轴和板块轴挤在一张表里，只有一个能当目录。** 表按 L0–L3 分四节，
   板块只存在于章节索引。想按板块读，就得在 55 行里跳着看。

## 为什么不违反 ADR-0009

ADR-0009 选"一个文件"的理由只有一句（原文 `:43`）：

> 新增 `spec/checklist.md`：把规则写成一张人读的表，成为**唯一事实源**
> （`rules/rules.json` 与 `spec/RULES.md` 同时下线，**避免双写**）。

**理由是"避免双写"，不是"一个文件更好"。** 真正的不变量是**一条规则只有一处定义**。
拆成 55 个文件、每条有唯一归属，照样满足——而且比原来更严：

| | 1.6.0（单文件） | 2.0.0（一规则一文件） |
|---|---|---|
| 一条规则的判据正文 | 1 处（表里一行） | 1 处（它自己的文件） |
| 判据句 | **3 处**：表的条目列 + `guide/` 正文 + 章节索引 | **1 处**：文件 H1（索引那一列是它的复制，见「代价」） |
| "有章节没条目"能不能悄悄发生 | 能，已经发生 3 次 | 结构上变难：判据文件自带「讲解」小节指向章节，反向指回去 |

## 决策

### 1. 规范名 = `板块/主题`，且 **ID 就是路径**

```
release/moving-tags   ↔   spec/rules/release/moving-tags.md
```

名字和路径不可能各说一套——这是比 Rust API Guidelines 更强的地方：
他们的 `C-CASE` 和 `naming.md` 是两套名字，必须靠 `checklist.md` 维护一张映射表。

### 2. 旧号 `R0xx` 永久保留为别名列

`rules/README.md` 每行第一列就是旧号。历史 PR、CHANGELOG、ADR、已发出去的采用记录
**一个字都不用改**。新写的引用一律用新名。

> **旧号永不复用、永不改；板块名一经发布不再改**（它编码在每条 ID 里）。

### 3. 一条规则一个文件

不聚类。理由：

- 文件名 = 规则名，辨识度拉满；
- `git log --follow <文件>` 就是这条规则的一生；
- 判据正文和它的解释、证据同处一地（治背景 2）；
- agent 只加载相关那一个文件，省 context。

### 4. 档位做索引的分节，不做目录

`rules/README.md` 按 L0 / L1 / L2 / L3 分四节，每节一张表。
目录只有一层：板块。

这是业界一致做法，无一例外：ASVS 把 L1/L2/L3 做成**列**，NIST 800-53 把 baseline 做成
**一份 control-ID 集合**（OSCAL profile），OpenSSF 做成 `p`/`s`/`g` **前缀**。
本库的符合性模型（"L0…目标档位的全部 `must` 满足"、采用记录要写"目标档位"）依赖档位可扫描，
所以它必须有实体落点——索引的分节就是落点。

### 5. 一律链到文件，不链到小节

`docs.yml` 的 lychee 参数是 `--offline --no-progress --accept 200,204,206,429`，
**没有 `--include-fragments`**，而 lychee 默认不校验 fragment。
所以 `xxx.md#小节` 写错了 CI 永远不红——**一种查不出来的腐烂**，而这个库的主题就是防腐。

一规则一文件之后，文件本身就是章节，锚点没有存在的理由，这个风险直接消失，也不用改 CI。

### 6. 板块 = 8 个，与 guide 八章 1:1

`adoption` `documents` `layout` `writing` `agent-config` `governance` `release` `settings`
↔ `guide/00`…`guide/07`。

每个规则文件自带「讲解」小节指向对应章节；被多个章节解释的（22 条）再加一节「跨板块」。

## 代价

- **三处受控双写**：索引的「判据」列 = 文件 H1；索引的「级别」列 = 文件首行注释；
  档位 = 索引分节 vs 文件首行注释。都是枚举值或短句，可逐字核对，
  但**本库不提供检查器**（ADR-0009），所以它们会漂。已写进 `AGENTS.md`「已知的坑」。
  这是继"中英标题数""章节索引"之后本库第 3、4、5 个已知漂移面——明写，不装。
- **55 个文件让"逐条比对"变成"逐个打开"**。缓解：索引一行一条，扫描在索引完成，
  只有要看判据时才点进文件。对人多了一步，对 agent 反而更省。
- **`guide/` 里 365 处 `R0xx` 引用这一轮没改**，仍是旧号。它们继续有效（索引能查），
  但"新旧两套名字并存"会持续一阵。要不要做正文改名，见「未解决」。
- **板块规模不均**：`documents/` 10 条 vs `adoption/` 1 条。没有掩盖，索引里就写着条数。
- **`spec/` 若要双语就是 55 对文件**。现在 `pairing` 只扫 `guide/*.md`，`spec/` 不在范围内——
  把这个事实当作"为什么 `spec/` 保持单语言"的正式理由。

## 未解决

- **`guide/` 正文要不要改用新 ID？** 365 处，含 19 处区间写法（`R064`–`R070` 这种）
  不能机械替换。收益是解释性文字也可辨识，代价是一个巨大的、难评审的 diff。
  本轮**没做**。
- **`R0xx` 会不会最终退役？** 只要还有历史采用记录指着它，就不会。可以预期它长期存在。

## 怎么回退

结构是纯机械的：`spec/rules/` 全部 55 个文件 + 索引，是从 `spec/checklist.md` 的 55 行
**逐行抽取**生成的，没有新写任何判据。回退 = `git revert` 这次重组的提交，
`spec/checklist.md` 原样回来，`R0xx` 从未改过所以零损失。
