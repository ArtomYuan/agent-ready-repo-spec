# ADR-0012：把"发布物怎么写"提升为可判定条目，而不是只留在指导正文里

- 状态：Accepted
- 日期：2026-11-18
- 决策者：@ArtomYuan
- 相关：[spec/checklist.md](../../spec/rules/README.md)（`R064`–`R070`）·
  [guide/06 §2](../../guide/06-信息该放哪.zh-CN.md) ·
  [ADR-0011](0011-github-management-rules.md) · [ADR-0009](0009-spec-only-no-tooling.md)

## 背景

[ADR-0011](0011-github-management-rules.md) 修的是"有章节没条目"：`guide/07` 写了一整章 GitHub 管理面，
清单里一条都没有。这次是**同一个病的另一处病灶**，而且更尴尬——

**[guide/06 §2](../../guide/06-信息该放哪.zh-CN.md) 早就把发布规矩写完了**：三件产物的分工（tag / Release / CHANGELOG）、
什么时候发、版本号怎么定、Release notes 的四节模板与 20 行上限、什么时候才配写发布流程文档。
写得比本 ADR 好。而它在清单里的规则 ID 引用数是 **0**。

于是这些规矩只有"读了那一章的人"会遵守。而发布这件事，恰恰是**不读那一章的人也会做的事**。

### 四条当场可证的坏后果

1. **没有锚点，"最新版本"是一句空话。** 本库 `SECURITY.md` 承诺"只对最新 `specVersion` 提供修复"，
   `spec/README.md` 定了 SemVer 策略——而 1.4.0 之前唯一的 tag 是 `v1` → `d60c3cc`，
   那棵树里还带着 `checker/` 与 `action.yml`（ADR-0009 之前的形态）。承诺指向一个不存在的东西。
2. **发布物是腐烂最快的文本，而没人会回来改它。** `1.5.0` 发布**当天**写进去的三句话，当天就全是假的：
   - "`GitHub App` 没有 Repository **metadata** 权限，`PATCH /repos` 返回 **422**，这一步改不了"
     —— 权限名错（是 `administration`）、错误码错（是 `403`）、结论错（卡住的原因是 installation 没批准扩权）；
   - "给 `spec/checklist.md`（**37 条**）出英文版" —— 同一天条目变成 48；
   - 仓库描述里的 `48 rules` —— 签完就删了。
   三处分别由 #37 / #38 / #39 修。**CHANGELOG 会被后续 PR 追加，Release 不会**——它是唯一一个
   发出去就没人再打开的产物，所以里面的时效性句子比正文更危险。
3. **"tag 永不改"这条写在表里的话，现实马上就要破例。** 本库正要把 `v1.4.0` 从
   "带着 1.5.0 文本的提交"切到真正的 1.4.0 提交（或改成发 `1.4.1`）。§2 的表说 tag "永不改"，
   却没有任何一条讲**真要改时怎么办**——而移动 tag 是对所有钉住它的人毁约，且损坏隐形：
   他们的构建变了，手上没有 diff 可读。
4. **本库自己定的 SemVer 策略，同样判不了任何人。** [spec/README.md](../../spec/README.md)「版本策略」写着
   "新增 `may`/`should` → minor，收紧判据 → major"——这是本库最硬的一条自我约束，而它在清单里的引用数也是 **0**。
   后果很具体：读者看到 `specVersion 1.5.0 → 1.6.0`，**无法判断这次升对没有**——
   因为"这批改动属于哪一类"只存在于 PR 描述里，而 PR 描述会沉进历史。
   补一句 `1.5.0 → 1.6.0：全是新增 should/may，属 minor`，就把一个不可验证的声明变成可验证的声明。这是 `R070`。

## 决策

新增 7 条，其中 6 条由 `guide/06 §2` 的既有正文**提出来**，`R070` 由 `spec/README.md`「版本策略」提出——都不是新发明：

| 条目 | 级别 | 一句话 |
|---|---|---|
| `R064` | L2 · should | 每个发布版本都有 tag **和** Release 页，tag 锚在发布提交上 |
| `R065` | L2 · should | Release 正文含四节：升级注意 / 新增·变更·修复 / 已知问题 / 校验 |
| `R066` | L2 · should | 发布物里不写会失效的计数和状态句 |
| `R067` | L2 · should | 移动 tag 要留痕，且优先发更正版本 |
| `R068` | L3 · may | 废弃 tag 标 *Superseded*，不删 |
| `R069` | L3 · may | 规范类项目在「已知问题」里列出自己不合格的条目 |
| `R070` | L2 · should | 版本号变更要写明升了哪一位、为什么 |

`specVersion` **1.5.0 → 1.6.0**（全是新增 `should` / `may`，按版本策略属 minor）。条目数 **48 → 55**。

`R067` 与 `R068` 是这次真正**新写**的部分——§2 里没有，是"要切 `v1.4.0`"这个具体动作逼出来的。
`R070` 也是新写的，动机是 reviewer 的一句话："版本号那里不需要加后面的解释吧？"——查完发现**没有任何一条规则**
回答这个问题，无论"需要"还是"不需要"。

## 备选方案与被否理由

| 方案 | 否掉的原因 |
|---|---|
| 只把规矩写进 `CONTRIBUTING.md`，不进清单 | 与 ADR-0011 同样的理由：没有判据的规矩只能靠"有人读到"。而发布是人人都会做的事。 |
| 加一个 CI 校验 Release 正文结构 | ADR-0009 禁止引入规则校验；且四节里有三节是判断（"升级注意"写没写到位），机器判不了，只会得到一个永远绿的假检查。 |
| `R067` 直接写成"禁止移动 tag" | 现实里会发生，本库马上就要发生一次。禁止的结果是让它**静默**发生——正是这条要防的事。 |
| 把这 6 条并入 `R014`（CHANGELOG 是行为契约） | `R014` 管的是累积记录，Release 管的是单次公告，两者的**可变性相反**：一个追加，一个发完即冻结。合并会让"哪部分能改"重新变模糊。 |

## 后果

**正面**

- 自查一个仓库时，"发布做得对不对"第一次有 6 个可勾选项，而不是"去读 guide/06"。
- `R066` 把本库这一周修了三次的那类错误变成一条**判据**，而不是三条勘误。
- `R067` 让接下来那次 tag 变更**必须先满足自己**才能执行——这是本库第一次用规范挡住自己的操作。

**代价（如实写）**

- `R065` / `R066` 的判定带主观成分："升级注意写没写到位""哪个数字算会失效的计数"要人来判。
  这是本库第一批**不能纯机械比对**的 L2 条目。诚实的边界是：`R064` / `R067` / `R068` 可机械判定，
  `R065` / `R066` / `R069` 需要读者，`R070` 一半一半——**那句话在不在**可以机械判定，
  **理由对不对**要人来判。
- 6 条全部**尚未经过外部仓库实测**，判据来自本库这一周自己的事故。下一批采样要专门验证它们是否可判定。
- 本库自己立刻就有活要干：`v1.4.0` 的处置必须按 `R067` 走，`1.6.0` 的 Release 要按 `R065`/`R066`/`R069` 重写。
- **`R066` 与本库现有做法有一处没解决的张力**：`README.md` 写着 "55 items"、`AGENTS.md` 写着"55 条唯一事实源"——
  这些同样是会失效的计数。`R066` 的范围**只覆盖发布物（Release 与 CHANGELOG）**，没有覆盖 README，
  理由是条目数放在首页有真实导航价值，而每次发版同步它是**已知且被接受的成本**
  （`CONTRIBUTING.md`「发布」第 2 步就是它）。要不要把这些计数也从 README 里去掉，是另一个决定，本 ADR 不替它做。

**反向选项（如果 reviewer 不同意）**

`R066` 可以降级为 `may`。它之所以是 `should`，是因为本库一周内踩了三次；如果你认为"发布物里的数字会过期"
属于常识、不需要条目，那它降到 `may` 不影响其余五条。
