# ADR-0005：把"下一步 / 非目标"变成发布必填项

- 状态：Accepted
- 日期：2026-11-17
- 决策者：@ArtomYuan
- 相关：[guide/06-信息该放哪.md](../../guide/06-信息该放哪.md) · [evidence/2026-11-17-repo-self-audit.md](evidence/2026-11-17-repo-self-audit.md) · [ADR-0004](0004-all-changes-via-pr.md)

## 背景

`guide/06` 把状态信息分成三种承载方式，可靠性从低到高：**靠记性写文档 < 模板必填 + 评审 < 写进工具**，
并推荐"已经有自动化发布路径时采用第三种"。

本仓库当时是**未采用**：`tools/publish-pr.ps1` 只强制 `-Message`，PR 描述由工具生成一段套话。
实测（2026-11-17 自审）：

- PR #3–#6 的描述各 **163 字**，全是同一个模板；
- 打开中的 issue **0 个**；
- 提交信息只有标题（+ squash 的 `#N`）。

结果：新会话能回答"做了什么"（标题 + diff），**回答不了"下一步做什么"**。

`guide/06` 里写的触发条件是"本章定稿后把发布参数改成必填"——章已定稿，条件成立。

## 选项

1. **保持现状**（套话模板）。零成本，但每次发布都不产生可交接的信息。
2. **模板必填 + 评审**（方式 B）。需要有一位评审者在 merge 前检查"下一步"栏；本仓库审批数为 0，等于没有闸。
3. **写进工具**（方式 C）。发布参数里强制"下一步"，缺了就发不出去；PR 描述结构化输出，并写进 squash 提交的正文。

## 结论

选 3。

- `-Next` 为**必填**；确实没有后续时显式写 `-Next "无"`（显式优于留空）。
- `-NotDoing` 可选，用于声明本次的非目标（防止下一个人"顺手补上"）。
- PR 描述固定四段：**改了什么 / 下一步 / 非目标 / 怎么验证的**。
- squash 提交的正文也带 `下一步：…`，这样 `git log` 不依赖 PR 页面也能读到。
- 忘记写的后果是**发布失败**，不是文档静默过期——这是本决策的全部意义。

## 后果

**正面**

- 每次发布都自动产生一份可交接的描述，无需额外维护任何状态文件；
- 新会话读最近一个 PR 就能回答"下一步做什么"（`guide/06` §2.5 的接手判据）；
- 与 `guide/06` 的"不建 PROGRESS / STATUS / sessions"完全一致——没有新增文件。

**负面**

- 每次发布多写一行的成本；写"无"时略显啰嗦；
- 仍依赖令牌与联网（与发布本身一致）；
- **PR 描述仍是自述**，证据依旧是 diff + CI——这一点不因本决策改变。

**破窗**：紧急情况下可临时用 `-Next "见 issue #N"` 代替手写，但**不允许**长期留空或全部写"无"。
若连续多次写"无"，说明项目已停滞或此机制形同虚设，应复审本 ADR。

**复审**：2027-01-31，或出现第二位维护者时（那时可回到方式 B）。
